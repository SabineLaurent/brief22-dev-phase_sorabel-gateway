# Q1 — Normaliser un corpus hétérogène et traiter les versions

> **Question du brief.** « Comment normaliser un corpus hétérogène (PDF techniques avec
> tableaux, HTML, Markdown) et traiter les versions multiples d'une même notice
> (dédoublonnage, champ version) ? »
>
> Tous les chiffres de ce document sont **mesurés** sur `data/corpus/` et reproductibles
> par le script du §9. Il remplace, pour cette question, `../docs/overview-rag.md` §Q1,
> écrit avant les chantiers 2 et 3 ; les écarts sont listés au §8.

**Décision : trois lecteurs, une structure unique — et les 400 éditions sont indexées,
chacune portant `is_current`. Le filtre de version s'applique dans chaque liste de
résultats *avant sa troncature*, jamais après la fusion. Une édition ancienne s'adresse par
clé de document + version, jamais par référence produit.**

## 1. Normaliser, c'est faire converger — pas convertir

Le premier jet prévoyait de tout convertir en Markdown pour préserver les tableaux.
**La sonde du corpus a supprimé le problème : aucun tableau dans les 400 éditions.** Il n'y
a rien à préserver, donc rien à convertir — un format pivot n'ajouterait qu'une étape et un
mode de panne de plus entre le fichier et l'index.

Normaliser veut dire ici : **faire converger trois formats vers une seule structure**, avec
un lecteur par format et aucune heuristique.

| Format | Texte | Titre | Version | Date | Référence |
|---|---|---|---|---|---|
| PDF (230) | `pypdf.extract_text()` | 1re ligne | ligne `Version :` | ligne `Date :` | ligne `Référence produit :` |
| HTML (90) | balises retirées | `<title>` | `<meta name="version">` | `<meta name="date">` | absente |
| Markdown (80) | corps après le frontmatter | `titre:` | `version:` | `date:` | dans le corps, jamais en frontmatter |

Le `doc_type` vient du **nom du dossier**, jamais du contenu. Détail d'ingestion qui compte :
`data/corpus/.DS_Store` traîne dans le dossier livré, un `rglob` naïf l'ingère.

## 2. La structure unique, et le vocabulaire qu'elle fixe

```python
@dataclass
class Edition:
    edition_id: str      # "fiches/REF-8842-v2.1"  — clé primaire de l'index, déterministe
    doc_key: str         # "fiches/REF-8842"       — regroupe les éditions d'un document
    version: str         # "2.1"
    is_current: bool     # l'édition la plus récente de sa clé de document
    texte: str
    titre: str
    date: str            # ISO, lue dans le contenu
    doc_type: str        # déduit du nom de dossier
    reference: str | None   # ancrée sur son étiquette ; absente en sav/ et notes/
    theme: str | None       # notes/ uniquement — imposé par la matrice d'accès
    url: str
```

**Trois mots, trois niveaux, et le mot « famille » est abandonné** — il désigne déjà une
famille d'articles chez un distributeur de matériel électrique
([description-corpus.md](description-corpus.md) §1) :

| Terme | Désigne | Champ |
|---|---|---|
| **édition** | un fichier sur le disque | `edition_id` |
| **document** | la chose, indépendamment de ses versions | `doc_key` |
| **clé de document** | le chemin privé de son suffixe `-vX.Y` | — |

`theme` n'est pas un champ de confort : c'est le point d'application d'E5 côté documentaire,
imposé par [../3-exposition-mcp-et-matrice-d-acces/Q3.md](../3-exposition-mcp-et-matrice-d-acces/Q3.md) §6.
Le modèle complet des métadonnées est en Q2.

## 3. Deux cas que le brief regroupe et qu'il faut séparer

**Doublon strict** — le même contenu deux fois. **Zéro hash d'octets dupliqué sur les 400
fichiers**, mesuré : il n'y a rien à dédoublonner dans le corpus livré.

Le seul risque réel de doublon est ailleurs, et il est certain : **la ré-ingestion**. D'où
`edition_id` déterministe et `upsert`, jamais `add` — sans quoi une seconde exécution double
l'index en silence et gonfle le rappel mesuré pour E6.

**Éditions multiples** — 50 documents en portent deux (30 fiches, 10 notices, 10 SAV). C'est
le vrai sujet, et il commence par une mesure.

## 4. Ce qui sépare réellement deux éditions — et ce n'est pas ce qu'on croit

| Similarité du texte entre l'édition ancienne et la récente | |
|---|---|
| minimum sur les 50 documents | **0,965** |
| médiane | 0,977 |
| lignes modifiées par document | **1 à 3**, médiane 2 |

| Collection | Documents | Ce qui change, exhaustivement |
|---|---:|---|
| `fiches/` | 30 | la ligne `Version`/`Date` · la ligne « Accessoires et produits associés » |
| `notices/` | 10 | la ligne `Version`/`Date` — **et rien d'autre** |
| `sav/` | 10 | la ligne `Version`/`Date` · la référence citée en exemple (2 occurrences) |

**Aucun prix, aucune caractéristique technique, aucune étape de procédure ne change entre
deux éditions.** Une notice v1.1 est son propre texte v1.0 avec un en-tête réécrit.

```
REF-5147 v1.0 → Accessoires et produits associés : REF-4963, REF-4316
REF-5147 v2.1 → Accessoires et produits associés : REF-4581, REF-6825
                (prix, garantie, fabricant, conditionnement : identiques)
```

**Deux conséquences, dans deux directions opposées :**

1. **il faut filtrer.** Deux éditions à 0,97 de similarité obtiennent des scores quasi
   identiques : sans filtre, elles occupent **deux places du top-5** pour un contenu unique.
   Le filtrage de version n'est pas une élégance, c'est ce qui empêche 20 % du top-5 d'être
   une redite ;
2. **le motif « historique » de `get_document` est plus faible ici qu'annoncé.**
   [../3-exposition-mcp-et-matrice-d-acces/Q1.md](../3-exposition-mcp-et-matrice-d-acces/Q1.md) §3
   le justifie par « que disait la procédure avant la mise à jour d'avril ? ». Sur ce
   corpus, la réponse est : **la même chose, avec un autre exemple.** Ce que le tool garantit
   reste vrai — atteindre ce que l'index masque, et citer une édition datée pour E1 — mais il
   ne révèle pas un contenu métier différent. À écrire ainsi plutôt qu'à surjouer.

> **Piège de mesure rencontré ici**, du même genre que ceux du §7 de la description du
> corpus : `difflib.SequenceMatcher` annonce **0,469** de similarité sur ces mêmes fichiers
> quand on le laisse à ses réglages par défaut. Au-delà de 200 éléments, il classe les
> caractères fréquents en « junk » et cesse de les apparier. Avec `autojunk=False`, **0,965**.
> Une conclusion sur la nature des éditions tirée du chiffre par défaut aurait été fausse.

## 5. Indexer les 400, et filtrer à la requête

Deux options tenaient, une fois la mesure du §4 connue :

| | Indexer 350 (la courante seule) | **Indexer 400 + `is_current`** |
|---|---|---|
| Recherche | rien à filtrer | filtre `is_current` à chaque requête |
| `get_document` d'une édition ancienne | **relire le fichier sur le disque** | même index, même chemin de code |
| Métadonnées d'une édition ancienne | à reconstruire à la lecture | déjà là, identiques à celles de la courante |
| Poids | 350 vecteurs | 400 vecteurs — **+14 % d'un index minuscule** |

**Retenu : les 400.** La raison n'est pas le volume, elle est qu'un second chemin d'accès
au corpus est un second endroit où la citation E1 peut diverger. Un titre relu à la volée
dans un PDF et un titre lu dans l'index sont deux valeurs qui *devraient* être égales — et
c'est exactement la forme que prennent les incohérences qu'on ne voit jamais venir.

### Où le filtre s'applique — et c'est ici que le schéma est corrigé

`schema-rag-avance.drawio` place `R1 · Filtre de version` **après la fusion RRF**, et
élargit `k_interne = 2 × k` pour compenser les places prises par les éditions périmées.

**Le filtre s'applique plus tôt : dans chaque liste, avant sa troncature.**

```
BM25    : scorer les 400, écarter les non-courantes, puis prendre les k premières
Chroma  : query(..., where={"is_current": True})   — le filtre est natif
Fusion  : RRF sur deux listes déjà propres
```

Trois raisons :

- **le `k_interne` élargi devient inutile** — il n'existait que pour compenser une pollution
  qu'on peut simplement ne pas produire ;
- **le rang devient interprétable.** Après un filtre post-fusion, « rang 3 » signifie
  « troisième, dont on a retiré des périmés » : deux exécutions sur des corpus différents ne
  se comparent plus. C'est le rang que RRF consomme, et c'est le chiffre qu'E6 publie ;
- **Chroma sait le faire, BM25 aussi** : filtrer après coûte du code là où filtrer avant
  n'en coûte pas.

**Pour E6, dans les deux configurations comparées, le nombre de candidats éligibles est le
même — 350.** La comparaison dense/hybride ne porte donc que sur la stratégie de recherche,
ce qui est la condition posée en Q5.

## 6. Le contrôle de cohérence est gratuit, il faut le prendre

La version figure deux fois : dans le nom de fichier et dans le contenu.

```python
assert version_du_nom == version_du_contenu, f"{chemin} : version incohérente"
```

**Mesuré : 400 éditions sur 400 sont cohérentes.** L'assertion ne protège donc pas la
livraison d'aujourd'hui — elle protège la prochaine, et elle coûte une ligne. Un document
dont on ne sait pas quelle édition il est n'a pas sa place dans un index qui filtre par
récence.

Cas particulier des **notes** : elles n'ont **aucun suffixe de version dans leur nom**
(0 sur 80), leur version vit dans le frontmatter et vaut `'1.0'` partout. Leur clé de
document est donc leur chemin, sans transformation, et elles sont toutes courantes.

## 7. Trier par récence est sûr ici — vérifié, pas supposé

L'édition retenue est la plus récente de sa clé de document. Deux critères possibles, la
date ou le numéro de version, et rien ne garantit *a priori* qu'ils s'accordent.

**Mesuré : sur les 50 documents à deux éditions, la version la plus haute porte toujours la
date la plus récente — 0 anomalie.** Les deux critères sont donc interchangeables sur ce
corpus.

**On trie sur la version, et on garde la date en contrôle.** Le numéro de version est ce que
l'auteur du document a décidé ; la date est ce qu'il a écrit. Quand les deux divergeront, ce
sera l'aveu d'une erreur de saisie, pas un cas à arbitrer en silence — et l'assertion du §6
l'aura déjà signalé.

## 8. L'adressage d'une édition ancienne : la clé de document, jamais la référence

`../docs/overview-rag.md` §Q1 écrit `get_document(reference, version="1.0")`. **Cette
signature ne peut pas fonctionner pour le cas qui justifie le tool.**

| Collection | Éditions anciennes | Référence produit |
|---|---:|---|
| `fiches/` | 30 | ancrée |
| `notices/` | 10 | ancrée |
| `sav/` | **10** | **aucune** — la seule REF citée est un exemple, et elle change d'une édition à l'autre |

Les procédures SAV sont précisément celles dont l'historique a un sens métier, et ce sont
les seules qu'une référence ne désigne pas. La signature retenue :

```
get_document(doc_key, version=None)     # version omise → l'édition courante
get_document("sav/proc-panne-batterie-electroportatif-01", version="1.0")
```

`reference` reste un **raccourci** valide pour `fiches/` et `notices/`, où elle identifie un
document — jamais la clé d'adressage. À reporter dans la signature du tool au catalogue MCP.

## 9. Ce que ce document corrige du premier jet

`../docs/overview-rag.md` §Q1 et `schema-rag-avance.drawio` divergeaient ; quatre points :

1. **350 indexés (overview) contre 400 indexés (schéma)** : tranché en 400 + `is_current`,
   avec la raison — un seul chemin d'accès au corpus, donc une seule source pour la
   citation E1 (§5) ;
2. **le filtre était placé après la fusion** avec un `k_interne` élargi ; il passe avant la
   troncature de chaque liste, et le `k_interne` élargi disparaît (§5) ;
3. **`get_document(reference, version)` est impossible** pour les 90 procédures SAV, qui
   n'ont pas de référence — l'adressage devient `doc_key` (§8) ;
4. **le tri se fait sur la version, pas sur la date**, les deux étant équivalents ici mais
   la version étant la donnée intentionnelle (§7). Et le vocabulaire « famille » /
   `file_family` est abandonné au profit de *clé de document* (§2).

## 10. Reproduction

```bash
# §3 — doublons stricts (attendu : 0)
find data/corpus -type f -not -name '.*' -exec shasum -a 256 {} \; \
  | awk '{print $1}' | sort | uniq -d | wc -l

# §6 — les notes n'ont pas de suffixe de version (attendu : 0 / 80)
ls data/corpus/notes | grep -c -- '-v[0-9]'
```

```python
# §4, §6, §7 — a lancer depuis la racine du depot
import pathlib, re, collections, difflib
from pypdf import PdfReader

root = pathlib.Path("data/corpus")
def texte(p):
    if p.suffix == ".pdf":
        return "\n".join(pg.extract_text() or "" for pg in PdfReader(str(p)).pages)
    t = p.read_text(encoding="utf-8", errors="replace")
    return re.sub(r"<[^>]*>", "", t) if p.suffix == ".html" else t

editions = collections.defaultdict(list)
for p in sorted(root.rglob("*")):
    if not p.is_file() or p.name.startswith("."):     # .DS_Store dans le dossier livre
        continue
    doc_key = re.sub(r"-v\d+\.\d+(?=\.\w+$)", "", str(p.relative_to(root)))
    m = re.search(r"-v(\d+\.\d+)\.", p.name)
    editions[doc_key].append((m.group(1) if m else "1.0", texte(p)))

lignes = lambda t: [l.strip() for l in t.splitlines() if l.strip()]
ecarts = []
for cle, eds in editions.items():
    if len(eds) < 2:
        continue
    a, b = [lignes(e[1]) for e in sorted(eds)]
    r = difflib.SequenceMatcher(None, " ".join(a), " ".join(b), autojunk=False).ratio()
    modif = [l for l in difflib.unified_diff(a, b, n=0)
             if l[:1] in "+-" and l[:3] not in ("---", "+++")]
    ecarts.append((r, cle, len(modif) // 2))

print(len(ecarts), "documents a deux editions")
print("similarite  min", f"{min(e[0] for e in ecarts):.3f}",
      " mediane", f"{sorted(e[0] for e in ecarts)[len(ecarts)//2]:.3f}")
# -> 50 documents ; min 0.965, mediane 0.977   (avec autojunk=True : 0.469 — §4)
print("lignes modifiees  max", max(e[2] for e in ecarts))          # -> 3

# §7 — version la plus haute == date la plus recente (attendu : 0 anomalie)
cle_version = lambda v: tuple(int(x) for x in v.split("."))
anomalies = 0
for cle, eds in editions.items():
    if len(eds) < 2:
        continue
    dates = {v: re.search(r"(\d{4}-\d{2}-\d{2})", t).group(1) for v, t in eds}
    if max(dates, key=cle_version) != max(dates, key=dates.get):
        anomalies += 1
print("anomalies version/date :", anomalies)                        # -> 0

# §6 — coherence version du nom / version du contenu (attendu : 0 sur 400)
```
