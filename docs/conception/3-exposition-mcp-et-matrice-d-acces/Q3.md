# Q3 — La matrice d'accès : forme, implémentation, point d'application

> **Question du brief.** « Comment implémentez-vous la matrice d'accès (client × tool ×
> collections × tables) et où la faites-vous respecter : à l'entrée du serveur, dans chaque
> tool, les deux ? »
>
> Les mesures documentaires du §6 portent sur `data/corpus/notes/` et sont reproductibles
> par les commandes du §11. La matrice colonne est celle de
> [../2-text-to-sql/Q3.md](../2-text-to-sql/Q3.md) §3, inchangée.

**Décision : la matrice est une donnée de configuration versionnée — un objet par profil,
trois sections — appliquée à trois étages dont deux seulement sont des garanties, et lue
partout par une fonction unique. Le client ne déclare jamais son profil.**

## 1. « Client × tool » est un raccourci : la matrice porte sur des profils

Le brief écrit « client × tool ». On indirecte, pour deux raisons :

- deux applications peuvent légitimement partager des droits (un second bot support n'est
  pas une quatrième ligne de matrice) ;
- un client renommé, remplacé ou dupliqué ne doit pas modifier des droits.

Deux tables, donc : `client → profil` (l'annuaire, qui bouge) et `profil → droits` (la
matrice, qui est gouvernée).

| Application cliente | Profil |
|---|---|
| bot Slack du support | `support` |
| poste des commerciaux | `commercial` |
| IDE des développeurs | `dev` |
| *tout le reste* | `default` — **zéro droit** |

## 2. D'où vient le profil : la question que le premier jet laissait ouverte

`docs/archives/03-chantier-mcp.md` la classait en point de variabilité (V14). Elle se
tranche, et sa réponse conditionne tout le reste : **si le client déclare son propre profil,
la matrice est décorative.**

**Le transport retenu est stdio** — celui du `scripts/mcp_client.py` attendu par le brief.
Sa propriété décisive : **le serveur est un processus lancé par le client**, pas un service
partagé. Il y a donc un processus serveur par poste, et le profil se fixe **à la ligne de
commande**, dans la configuration du poste :

```json
{ "mcpServers": { "sorabel": {
    "command": "python", "args": ["-m", "mcp_server"],
    "env": { "SORABEL_PROFILE": "support" } } } }
```

Le profil est lu **une fois au démarrage**. Il n'est ni un argument de tool, ni un champ de
requête : le LLM du client ne peut pas l'écrire, parce qu'il n'existe nulle part dans ce
qu'il manipule.

> **Correction portée au chantier 2** — faite, voir
> [../audit-coherence.md](../audit-coherence.md) D1. `catalogue-tools.md` écrivait
> `get_schema(profil)` et `ask_database(question, profil)`, en précisant « fourni par le
> serveur, jamais par le client ». L'intention était juste, la signature la contredisait : un
> paramètre présent dans l'`inputSchema` **sera** rempli par le LLM. Le paramètre a disparu
> des signatures exposées — `get_schema()` n'a plus aucun argument, `ask_database(question)`
> n'en a qu'un — et il reste un argument des fonctions internes.

*Si le transport devenait HTTP*, le serveur serait partagé et le profil viendrait d'un
jeton d'authentification vérifié par requête — jamais d'un en-tête libre.

**Et l'étage 1 en dépend aussi** — correction portée depuis [Q5](Q5.md) §10, qui écartait la
première rédaction de ce paragraphe (« seule la ligne *d'où vient le profil* dépend du
transport »). La spécification 2026-07-28 encadre le filtrage du catalogue : le jeu de tools
« **MUST NOT** vary per-connection », mais il « **MAY** vary by the authorization presented
on the request — since credentials are per-request input, not connection state ». En stdio,
un processus serveur par poste : le catalogue ne *varie* pas, il *est* constant pour la vie
du processus — conforme. Sur un serveur HTTP partagé, filtrer d'après un profil de processus
ne le serait plus ; le filtrage devrait suivre l'autorisation de chaque requête.

## 3. La matrice, en un seul fichier

```yaml
# mcp_server/matrice.yaml — donnée de configuration, versionnée, jamais du code
profils:
  default:            { tools: [], collections: [], themes_notes: [], tables: {} }

  support:
    tools:        [answer_question, search_docs, get_document, list_sources,
                   get_schema, ask_database, check_stock, order_status]
    collections:  [fiche_technique, notice, procedure_sav, note_interne]
    themes_notes: [alerte-qualite, logistique, retour-terrain]     # liste blanche, §6
    tables:
      produits:  [ref, nom, categorie, fabricant, unite, prix_vente_ht, actif]
      stocks:    [ref, entrepot, quantite, seuil_reappro]
      commandes: [id, client_id, date_commande, statut, montant_ht]
      clients:   [id, raison_sociale, segment, ville]
      ventes:    [commande_id, ref, quantite, prix_unitaire_ht, remise_pct]

  commercial:
    tools:        [... les huit ...]
    collections:  [fiche_technique, notice, procedure_sav, note_interne]
    themes_notes: [alerte-qualite, logistique, retour-terrain,
                   politique-tarifaire, reunion-achat]
    tables:                                    # + les trois colonnes sensibles
      produits:  [..., prix_achat_ht, marge_pct]
      ventes:    [..., marge_ht]

  dev:
    tools:        [answer_question, search_docs, get_document, list_sources, get_schema]
    collections:  [fiche_technique, notice, procedure_sav]
    themes_notes: []
    tables:       <mêmes que support>           # la forme, jamais le contenu — §9
```

**Trois propriétés, toutes délibérées :**

1. **liste blanche partout.** Une colonne, une collection ou un thème ajouté demain est
   refusé par défaut. Le principe vient du chantier 2 et vaut ici à l'identique ;
2. **`default` est un profil, pas une exception.** `matrice.get(profil) or DEFAULT` — jamais
   de `KeyError`, jamais de `None` qui se propage. La matrice est *totale* : un profil
   inconnu produit un refus propre et journalisé, pas une trace de pile ;
3. **de la configuration, pas du code.** Retirer le profil `dev` ou rouvrir un thème coûte
   une ligne relue en revue, sans redéploiement de logique.

## 4. Trois étages, dont deux sont des garanties

| Étage | Ce qu'il tranche | Pourquoi là | Nature |
|---|---|---|---|
| **`tools/list`** | quels tools le client voit | un tool visible mais toujours refusé transforme la matrice en source d'échecs pour le LLM client | **ergonomie** |
| **Intercepteur d'entrée** | ce profil a-t-il droit à *ce tool* ? | décidable sans connaître les arguments ; un seul point à auditer ; refuse au plus tôt, avant tout accès aux données | **garantie** |
| **Dans le tool** | a-t-il droit à *ces collections, thèmes, tables, colonnes* ? | indécidable avant de connaître les arguments et le SQL généré : c'est le seul endroit où E5 est vérifiable | **garantie** |

Le test d'acceptance « un client non autorisé sur un tool → refus clair et journalisé »
impose que **l'étage 2 existe indépendamment de l'étage 1** : rien n'empêche un client
d'invoquer un nom de tool qu'il n'a pas listé.

> **Règle : l'étage 3 ne fait aucune hypothèse sur l'étage 2.** Un tool appelé directement
> par un test, un script ou un futur transport doit refuser tout seul. Une barrière qui
> suppose qu'une autre barrière l'a précédée n'en est pas une.

## 5. Une seule fonction, huit appelants

L'intercepteur seul ne couvre pas E5 ; la vérification recopiée dans huit tools garantit
l'oubli, et un oubli ici est une brèche silencieuse. La sortie n'est pas de choisir un
endroit, c'est de **n'écrire la règle qu'une fois** :

```python
def autoriser(profil: str, ressource: tuple) -> None:
    """Lève Refus(code, message, hint) ou ne fait rien. Seul lecteur de matrice.yaml."""
    # ("tool", "ask_database") | ("collection", "note_interne")
    # ("theme", "politique-tarifaire") | ("colonne", "produits", "marge_pct")
```

**Le tool ne décide pas, il demande.** Aucun `if profil == "support"` dans le code métier :
un test de profil écrit en dur est une ligne de matrice invisible, absente du fichier
gouverné et absente de la revue.

## 6. Le grain documentaire : le thème, pas la collection

Le chantier 1 laissait le choix ouvert — fermer `notes/` entièrement au support, ou
seulement le thème `politique-tarifaire`. **La mesure tranche, et écarte les deux options.**

| Thème (16 notes chacun) | `marge` | `tarif` | `remise` / négociation | mention « Diffusion restreinte » |
|---|:--:|:--:|:--:|:--:|
| `politique-tarifaire` | **16** | **16** | — | **16** |
| `reunion-achat` | — | — | **16** | **0** |
| `alerte-qualite` | — | — | — | 0 |
| `logistique` | — | — | — | 0 |
| `retour-terrain` | — | — | — | 0 |

```
Compte rendu réunion achats
Négociation en cours avec Fixor : conditions de remise sur volumes revues pour
Visserie. Prochaine échéance contractuelle au trimestre prochain.
        — note-…-reunion-achat, sans mention de diffusion restreinte
```

**Trois conséquences :**

- **le marqueur « Diffusion restreinte » n'est pas un critère.** Il couvre exactement 16
  notes sur les 32 sensibles. Filtrer sur lui laisserait sortir les conditions de
  négociation fournisseur ;
- **fermer la collection entière coûte trop.** 64 notes non sensibles deviendraient
  inaccessibles au support, dont les 16 `alerte-qualite` — précisément son métier ;
- **le thème est un grain fiable** : dérivé du nom de fichier, régulier sur les 80 notes,
  cinq valeurs exactement. *Conséquence pour le chantier 1 : `theme` devient une métadonnée
  de chunk pour `note_interne`, au même titre que `doc_type` et `version`.*

**Décision : liste blanche de thèmes par profil** (§3). Un sixième thème apparaîtrait fermé
à tous jusqu'à arbitrage explicite — ce qu'une liste noire fondée sur les mots « marge » ou
« Diffusion restreinte » n'aurait pas fait.

## 7. Le même secret par deux portes — ce que seul ce chantier pouvait voir

Le chantier 2 a montré que `prix_achat_ht`, `marge_pct` et `marge_ht` sont **un seul secret
en trois exemplaires**, et a fermé les trois au support. La mesure ci-dessus prolonge le
raisonnement hors de la base :

| Porte | Ce qui sort | Fermé par |
|---|---|---|
| SQL | `produits.prix_achat_ht`, `marge_pct`, `ventes.marge_ht` | matrice colonne (chantier 2) |
| Corpus | conditions d'achat négociées, marges cibles, en texte | matrice de thèmes (§6) |

**Fermer l'une sans l'autre ne protège rien.** Un profil support privé de `marge_pct` mais
autorisé sur `note_interne` obtient les marges cibles par `answer_question` — avec citation
de la source, proprement, sans qu'aucune barrière ne se déclenche.

> **La fermeture par dérivation du chantier 2 ne s'arrête pas au bord de la base.**
> C'est la vérification que ni le chantier 1 ni le chantier 2 ne pouvaient faire seuls, et
> la raison d'être d'une matrice unique plutôt que de deux matrices cohérentes par hasard.

## 8. Le cas des collections demandées explicitement

`answer_question`, `search_docs` et `list_sources` acceptent un argument `collections`. Le
serveur ne peut pas se contenter d'intersecter en silence :

| Ce que fait le client | Ce que fait le serveur | Pourquoi |
|---|---|---|
| ne précise rien | recherche sur **toutes** les collections et thèmes du profil | cas nominal |
| demande une collection autorisée | filtre dessus | cas nominal |
| demande une collection **interdite** | **refus `perimetre_interdit`**, journalisé | une intersection silencieuse renverrait un résultat vide ou partiel que le client lira comme « rien à ce sujet » |

Le filtre effectivement appliqué à l'index est **construit par le serveur depuis la
matrice**, jamais recopié depuis l'argument client. L'argument sert à *réduire* un
périmètre, jamais à le définir.

C'est le même arbitrage qu'au chantier 2 sur les colonnes : **on refuse en nommant, on ne
rogne pas en silence** — un résultat amputé est cru complet.

### La forme du filtre : une disjonction, pas une conjonction

La première rédaction de ce paragraphe donnait `where={"doc_type": {"$in": [...]}, "theme":
{"$in": [...]}}`. **Cette forme ne remonte que des notes.** Deux clés dans un même `where`
valent un `$and`, et la documentation Chroma est explicite sur les clés absentes : *« if a
metadata key is missing for a document, most comparison operators (`==`, `>`, `<`, `>=`,
`<=`, `is_in()`) will evaluate to `false` »*. Or `theme` n'existe que sur les 80 notes
([../1-rag-avance/Q2.md](../1-rag-avance/Q2.md) §3) : les 270 autres éditions courantes
échouent sur la clause `theme` et disparaissent, sans qu'aucune erreur ne le signale.

**Le thème ne qualifie qu'une seule collection ; le filtre doit donc être une disjonction.**

```python
def filtre_index(profil: str) -> dict:
    """Seul producteur du `where`. Lit matrice.yaml, jamais l'argument client."""
    m = matrice(profil)
    branches = []
    autres = [c for c in m.collections if c != "note_interne"]
    if autres:
        branches.append({"doc_type": {"$in": autres}})
    if "note_interne" in m.collections and m.themes_notes:
        branches.append({"$and": [{"doc_type": {"$eq": "note_interne"}},
                                  {"theme": {"$in": m.themes_notes}}]})
    if not branches:                       # profil `default`, ou périmètre vidé
        raise Refus("perimetre_interdit", "aucune collection ouverte à ce profil")
    perimetre = branches[0] if len(branches) == 1 else {"$or": branches}
    return {"$and": [{"is_current": {"$eq": True}}, perimetre]}
```

Trois pièges que cette forme traite, et qui sont la raison de l'écrire une fois pour toutes :

- **un périmètre vide ne produit pas un filtre vide.** `where={}` ne filtre rien : le profil
  `default`, censé n'avoir aucun droit, lirait **tout le corpus**. C'est la panne symétrique
  de celle du paragraphe précédent, et la plus grave des deux — d'où le refus explicite ;
- **une seule branche n'est pas un `$or`.** `$and` et `$or` attendent un tableau
  d'opérandes ; le profil `dev` (trois collections, aucun thème) produit une branche unique,
  à ne pas envelopper ;
- **`is_current` reste une clause à part**, en `$and` avec le périmètre. Le filtre de version
  et le filtre de gouvernance ne se mélangent pas : le premier fixe le dénominateur de la
  mesure E6 à 350 ([../1-rag-avance/Q1.md](../1-rag-avance/Q1.md) §5), le second dépend du
  profil et n'a pas à entrer dans cette mesure.

**Conduite retenue à l'ingestion, en conséquence : la clé `theme` est *omise* pour les 320
éditions qui n'en portent pas**, jamais remplie d'une chaîne vide ni d'une sentinelle. Une
sentinelle qu'il faudrait penser à ajouter à chaque liste blanche serait exactement le mode
de panne qu'on vient de corriger. Cela tranche le point laissé ouvert en
[../1-rag-avance/Q2.md](../1-rag-avance/Q2.md) §3.

> La forme ci-dessus est **documentée, pas exécutée** : `chromadb` n'est pas installé dans
> l'environnement du projet. Le premier jour du développement la vérifie sur les quatre
> profils, avec la version figée. Un test qui compte les éditions éligibles par profil suffit
> à voir la panne si elle revient : **350 pour `commercial`** (270 + les 80 notes, cinq
> thèmes ouverts), **318 pour `support`** (270 + 48 notes, trois thèmes sur cinq à 16 notes),
> **270 pour `dev`** (aucune note), **refus pour `default`**.

### Les deux tools qui ne passent pas par ce filtre

`filtre_index` protège les tools de **similarité**. Les deux tools d'**identité**
([Q1](Q1.md) §« Décision ») ne l'empruntent pas, et le thème doit y être vérifié autrement :

| Tool | Ce qui remplace le filtre |
|---|---|
| `get_document(doc_key, version)` | `doc_key` **porte** la collection et le thème — tous deux dérivés du nom de fichier (§6). L'autorisation est donc décidable sur le seul argument, **avant tout accès à l'index** : `autoriser(profil, ("collection", …))`, puis `autoriser(profil, ("theme", …))` s'il s'agit d'une note |
| `list_sources(collections)` | l'inventaire est construit depuis `filtre_index(profil)`, jamais par un parcours du corpus — sans quoi il publierait l'existence des notes fermées |

**Le refus est `perimetre_interdit`, jamais `introuvable`.** Nommer ce qui est refusé est la
règle de ce paragraphe, et le catalogue des portes est public ([Q4](Q4.md) §2) ; répondre
« introuvable » ferait croire à une absence et supprimerait le recours. Conséquence assumée :
un `doc_key` inventé sous un thème fermé reçoit `perimetre_interdit` alors qu'il n'existe
pas — ce qui n'apprend rien sur son existence, et c'est le bon compromis.

Sans cette vérification, la fermeture du §7 est contournable par un simple chemin de
fichier : `get_document("notes/note-2025-04-24-politique-tarifaire-71")` rendrait au profil
`support` une marge cible que `search_docs` lui refuse.

## 9. La matrice `profil × tool`

| Tool | `default` | `dev` | `support` | `commercial` |
|---|:--:|:--:|:--:|:--:|
| `answer_question` | ✗ | ✓ | ✓ | ✓ |
| `search_docs` | ✗ | ✓ | ✓ | ✓ |
| `get_document` | ✗ | ✓ | ✓ | ✓ |
| `list_sources` | ✗ | ✓ | ✓ | ✓ |
| `get_schema` | ✗ | ✓ | ✓ | ✓ |
| `ask_database` | ✗ | ✗ | ✓ | ✓ |
| `check_stock` | ✗ | ✗ | ✓ | ✓ |
| `order_status` | ✗ | ✗ | ✓ | ✓ |

**`ask_database` est bien accordé au support** : les questions SQL-17 → SQL-20 du jeu
d'évaluation sont refusées **sur le périmètre**, pas sur le tool. Retirer le tool au support
ferait passer les tests pour la mauvaise raison.

**`dev` a `get_schema`, mais aucun tool de lecture de données.** La distinction n'est pas un
compromis, elle est nette : `get_schema` renvoie la **forme** (DDL commenté, énumérations,
plage temporelle, conventions métier), les trois autres renvoient du **contenu**. Un
intégrateur a besoin de la première pour coder ; le contenu ne lui apprendrait rien qu'il
puisse mettre dans son code.

Son périmètre de tables est donc **celui du `support`** : les trois colonnes sensibles
restent fermées, par cohérence avec la fermeture par dérivation du §7 — décrire `marge_pct`
à qui ne doit pas la lire, c'est déjà en publier l'existence et la définition.

> **Un périmètre de tables non vide n'implique pas un accès aux données.** Ce sont les tools
> ouverts qui décident de ce qui sort ; la matrice de colonnes borne ce qu'ils peuvent en
> dire.

## 10. Ce que ce document corrige du premier jet

1. **V14 est tranché** : le profil vient de l'environnement de lancement, propriété du
   transport stdio, et disparaît des signatures de tools (§2) ;
2. **V12 est tranché par la mesure**, et autrement que prévu : ni collection entière ni
   marqueur textuel, mais une liste blanche de thèmes (§6) ;
3. **trois étages au lieu de deux** : le filtrage de `tools/list` manquait, et avec lui la
   raison pour laquelle il ne remplace pas le refus (§4) ;
4. **la table `lignes_commande` n'existe pas** — l'archive la citait ; la base porte
   `ventes`, et `ventes` n'est pas interdite au support : seule `marge_ht` l'est (chantier 2
   §3).

## 11. Reproduction

```bash
# §6 — croisement marqueur sensible × thème (attendu : 16 politique-tarifaire / 16 reunion-achat)
for m in marge tarif remise "Diffusion restreinte"; do
  printf "%-22s " "$m"
  grep -rliE "$m" data/corpus/notes \
    | sed -E 's#.*/note-[0-9-]+-##; s/-[0-9]+\.md//' | sort | uniq -c | tr '\n' ' '
  echo
done

# §7 — aucune autre collection ne parle de marge (attendu : 0 0 0)
for d in fiches notices sav; do grep -rli marge data/corpus/$d | wc -l; done
```
