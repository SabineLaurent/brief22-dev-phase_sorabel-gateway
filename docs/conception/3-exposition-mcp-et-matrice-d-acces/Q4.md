# Q4 — Ce que renvoie un refus, et ce que le journal retient

> **Question du brief.** « Que renvoie un appel refusé (message, code) et que
> journalisez-vous pour chaque appel (E5) ? »
>
> Les codes de sortie de `ask_database` sont posés dans
> [../2-text-to-sql/catalogue-tools.md](../2-text-to-sql/catalogue-tools.md) §« Codes de
> sortie » et [../2-text-to-sql/Q5.md](../2-text-to-sql/Q5.md) §6. Les trois étages de
> contrôle qui produisent les refus sont établis en [Q3](Q3.md) §4.

**Décision : un refus est un résultat, pas une panne.** Il part vers le client comme une
réponse ordinaire, marquée `isError: true`, portant un triplet `{code, message, hint}`. Le
journal, lui, obéit à la règle inverse de la matrice d'accès : il retient **toujours
l'entrée, jamais la sortie**.

Un même appel produit donc deux écritures qui n'ont ni le même lecteur, ni le même besoin.

| | Le refus | Le journal |
|---|---|---|
| Lecteur | le **LLM** du client, dans la seconde | un **humain**, des jours plus tard |
| Ce qu'il doit permettre | se corriger sans réessayer à l'identique | prouver qu'E5 a été tenue |
| Donc il contient | pourquoi, et ce qui reste possible | qui, quoi, quand, **quelle barrière** |

## 1. La forme : `isError`, pas une erreur de protocole

La spécification MCP (révision **2026-07-28**) sépare deux mécanismes de signalement :

- les **erreurs de protocole** — tool inconnu, requête malformée, serveur en panne — qui
  remontent en erreur JSON-RPC ;
- les **erreurs d'exécution** — échec d'API, validation d'entrée, **règle métier** — qui
  remontent dans un résultat normal avec `isError: true`, et dont la spec dit
  explicitement qu'elles sont là *« pour permettre au modèle de se corriger »*.

Nos refus sont tous des règles métier. Ils passent donc par `isError`.

```json
{
  "resultType": "complete",
  "content": [{ "type": "text", "text":
    "perimetre_interdit — la colonne marge_ht n'est pas ouverte au profil support. Le prix de vente HT et les quantités le sont." }],
  "isError": true
}
```

`resultType` est apparu avec cette révision : un refus est un résultat **abouti**, d'où
`complete`. La seule autre valeur admise sur `tools/call`, `input_required`, ouvre un
troisième canal que nous n'empruntons pas — motifs en [Q5](Q5.md) §2-3.

> **Pourquoi ce n'est pas une préférence de style.** Une erreur JSON-RPC est interceptée
> par le client et **n'atteint pas le modèle**. Le `hint` prévu en [Q2](Q2.md) §7 serait
> écrit pour personne, et le LLM réessaierait la même question — c'est exactement le
> scénario que le SEP 1303 décrit pour justifier d'avoir déplacé la validation d'entrée
> hors du protocole.

*Écart de version, reporté :* `catalogue-tools.md` citait la révision **2025-11-25**, celle
d'avant ce déplacement — il cite désormais **2026-07-28**, et la citation elle-même a été
remplacée, la phrase invoquée n'existant pas dans la révision courante
([../audit-coherence.md](../audit-coherence.md) D3). Le catalogue MCP complet citera la même.

## 2. Le cas limite : un tool que le profil ne voit pas

Le profil `dev` ne reçoit pas `ask_database` dans son `tools/list` ([Q3](Q3.md) §4, étage 1).
S'il l'appelle quand même, deux réponses sont défendables :

| Réponse | Ce qu'elle dit | Pourquoi on ne la retient pas |
|---|---|---|
| erreur de protocole *Invalid params* — tool inconnu | « ce tool n'existe pas » | **c'est faux**, et le test d'acceptance exige « un message clair » — un code `-32602` n'en est pas un |
| `isError` + `tool_interdit` | « ce tool existe, il ne vous est pas ouvert » | ✔ retenue |

Masquer l'existence du tool ne protégerait d'ailleurs rien : **le catalogue des huit tools
est un livrable public du brief**, remis aux équipes clientes. Le secret porte sur les
données, jamais sur la liste des portes.

## 3. Le triplet `{code, message, hint}`

| Champ | Rôle | Règle de rédaction |
|---|---|---|
| `code` | stable, lu par le client | jamais reformulé, jamais traduit — c'est la clé du journal |
| `message` | une phrase | **nomme ce qui est refusé** — règle de [Q3](Q3.md) §8 : on refuse en nommant, on ne rogne pas en silence |
| `hint` | ce qui reste possible | la seule partie qui change le comportement du LLM |

Sur SQL-17 (« quelle est la marge sur la REF-8842 ? », profil `support`) :

```
code    : perimetre_interdit
message : la colonne marge_ht n'est pas ouverte au profil support
hint    : prix_vente_ht et quantite le sont ; la marge s'obtient auprès du profil commercial
```

Sans le `hint`, le modèle reformule (« et le taux de marge ? ») et retombe sur
`produits.marge_pct`, l'autre colonne fermée — deux refus au lieu d'un, pour la même cause.

## 4. La ligne de partage : quatre refus, douze codes

Le chantier 2 a posé huit codes de sortie pour le seul `ask_database`. Ce document **ne les
remplace pas** : il les étend aux quatre tools documentaires et tranche, pour chacun, s'il
porte `isError`.

> **Règle : `isError` marque ce que le serveur a refusé de faire ou n'a pas pu faire —
> jamais ce qu'il a fait et qui n'a rien donné.**

| Code | Refus | `isError` | Origine, et où il est exercé |
|---|:--:|:--:|---|
| `ok` | | non | résultat nominal |
| `clarification` | | non | ambiguïté de question — SQL-23, SQL-24 |
| `aucune_ligne` | | non | clé bien formée, absente — SQL-08 |
| `introuvable` | | non | référence ou version inexistante — `get_document` |
| `ambiguite_donnees` | | non | plusieurs lignes là où une est attendue — SQL-10, SQL-12, SQL-18 |
| `hors_corpus` | | non | meilleur score sous le seuil (barrière 1) — RAG-23 → 30 |
| `contexte_insuffisant` | | non | seuil franchi, extraits qui ne portent pas la réponse (barrière 2) |
| `tool_interdit` | ✔ | **oui** | le profil n'a pas ce tool — [Q3](Q3.md) §4, étage 2 |
| `perimetre_interdit` | ✔ | **oui** | cible hors matrice : colonne SQL **ou** thème de notes — SQL-17 → 20, [Q3](Q3.md) §6-7 |
| `ecriture_refusee` | ✔ | **oui** | demande de modification — SQL-13 → 16 |
| `hors_schema` | ✔ | **oui** | la question ne porte pas sur la base — SQL-21, SQL-22 |
| `erreur_execution` | | **oui** | timeout, plafond de lignes — ch. 2, Q2 §3 C4 |

Trois conséquences, qui sont les vrais arbitrages de cette section :

**`introuvable` n'est pas un refus** — c'est le pendant documentaire d'`aucune_ligne`. Une
référence bien formée qui ne désigne rien est un **constat sur le monde**, pas une décision
du serveur. Les traiter différemment selon qu'on interroge la base ou le corpus n'aurait
aucune justification.

**`hors_corpus` non plus, et c'est le point discutable.** L'argument contraire est réel :
sans `isError`, un LLM client pourrait être tenté de compléter avec ses propres
connaissances, ce qu'E1 interdit. Mais `isError` n'est pas un mécanisme anti-hallucination
— E1 est tenue en amont, par `answer_question` qui **ne rédige pas** quand la barrière
tombe, et par le `message` qui dit l'absence de couverture. Marquer `isError` un appel qui
s'est déroulé exactement comme prévu casserait la lecture du journal (§6) pour un bénéfice
qui n'existe pas.

**`erreur_execution` porte `isError` sans être un refus.** C'est le seul code des douze où
les deux notions se séparent : rien n'a été refusé, l'exécution a échoué. La colonne
« Refus » du tableau et la colonne `isError` ne sont donc pas redondantes.

## 5. Deux barrières documentaires, deux codes

`hors_corpus` et `contexte_insuffisant` restent distincts parce que les deux barrières du
chantier 1 échouent pour des raisons opposées : la première est **déterministe et aveugle
au contenu**, la seconde **lit le contenu mais reste probabiliste**.

À l'usage, l'une dit « je n'ai rien trouvé », l'autre « j'ai trouvé, ça ne répond pas ». Le
recours de l'utilisateur n'est pas le même : reformuler pour la première, préciser pour la
seconde.

## 6. Le piège est dans le journal, pas dans l'affichage

Marquer `aucune_ligne` ou `hors_corpus` en `isError` les ferait journaliser `denied`. Le
fichier censé prouver la gouvernance compterait alors des refus qui n'ont jamais eu lieu, et
la lecture d'E5 deviendrait fausse dans le sens le plus gênant : elle **surestimerait** la
sévérité du système.

Confondre « je n'ai pas le droit » et « il n'y en a pas » produit une réponse fausse au sens
métier même avec un code irréprochable (ch. 2, [Q5](../2-text-to-sql/Q5.md) §6).

## 7. La langue des codes : le français, et [Q3](Q3.md) est corrigé

Q3 annonçait `FORBIDDEN_TOOL` et `FORBIDDEN_SCOPE`. Le chantier 2 avait déjà posé ses huit
codes en français, et le jeu d'évaluation type ses questions dans le même vocabulaire
(`metier`, `ecriture`, `table_interdite`, `ambigue`, `reference_exacte`, `couverte`,
`hors_corpus`). On aligne sur l'existant : deux conventions dans un même catalogue
coûteraient une table de correspondance à maintenir, pour rien.

| Ancien | Nouveau | Où c'est corrigé |
|---|---|---|
| `FORBIDDEN_TOOL` | `tool_interdit` | [Q3](Q3.md) §Renvois |
| `FORBIDDEN_SCOPE` | `perimetre_interdit` | [Q3](Q3.md) §8 et §Renvois |
| `colonne_interdite` | `perimetre_interdit` | chantier 2 : [`catalogue-tools.md`](../2-text-to-sql/catalogue-tools.md), [`Q5.md`](../2-text-to-sql/Q5.md), les deux `.drawio` |

**Un seul code pour deux périmètres** : qu'il vise une colonne SQL ou un thème de notes, le
refus est le même et le recours aussi — demander l'habilitation. Le nom `colonne_interdite`
était par ailleurs déjà en tension avec le jeu d'évaluation, qui type ces mêmes questions
`table_interdite` alors que le chantier 2 a établi que la granularité est **la colonne**
(ch. 2, [Q3](../2-text-to-sql/Q3.md) §3). `perimetre_interdit` clôt les deux écarts.

> ⚠ **Les `.png` exportés sont à régénérer** — ils précèdent toutes les modifications
> ci-dessous. Blocs touchés depuis leur export, dans `flux-text-to-sql-v2.drawio` : `R3`
> (`colonne_interdite` → `perimetre_interdit`, §7), `R0` (`non_autorise` → `tool_interdit`),
> `N7` (le `llm_as_judge` remplacé par les trois contrôles de code) et les deux signatures
> de tools, dont le paramètre `profil` a disparu ([Q3](Q3.md) §2) ; dans
> `schema-rag-avance_V2.drawio` : le chiffre BM25 de `REF-8842`, porté à 3 éditions
> courantes sur 350. L'export demande `drawio`, absent de cet environnement — à faire à
> l'ouverture du fichier.

## 8. Le journal : un événement par appel, autorisé comme refusé

Fichier **JSONL append-only**, une ligne par appel.

| Champ | Contenu | |
|---|---|---|
| `ts` | horodatage | |
| `client`, `profil` | identité de l'appelant, résolue à l'entrée ([Q3](Q3.md) §2) | |
| `tool`, `args` | l'appel demandé, intégralement | |
| `decision` | `allowed` \| `denied` | |
| `etage` | `tools_list` \| `entree_serveur` \| `tool` | **ajouté** |
| `code` | l'un des douze codes du §4 | |
| `sql` | requête générée et/ou exécutée | |
| `n_rows` | **nombre** de lignes retournées | |
| `citations` | références citées, pour les tools documentaires | |
| `latency_ms` | durée | |

**`decision` se déduit du code, pas l'inverse** : `denied` pour les quatre refus, `allowed`
partout ailleurs — y compris pour `erreur_execution` et `hors_corpus`. Le champ reste écrit
en clair plutôt que recalculé à la lecture : un journal doit être lisible sans connaître la
table des codes.

**`etage` est ce qui rend la défense en profondeur vérifiable.** Sans lui, le journal dit
qu'un appel a été refusé mais pas *par quelle barrière* — or [Q3](Q3.md) §4 pose que
l'étage 3 ne suppose jamais l'étage 2. Un test qui appelle un tool directement, sans passer
par l'intercepteur, doit pouvoir se lire dans le journal : `etage: "tool"` en est la preuve.

**Contrainte de transport.** En stdio, `stdout` est le canal du protocole : tout `print` le
corrompt. Le journal va en fichier, le diagnostic sur `stderr`. Ce n'est pas une préférence
d'implémentation, c'est une propriété du transport retenu en [Q3](Q3.md) §2.

## 9. L'entrée, oui ; la sortie, jamais

`args` contient la question en langage naturel — donc parfois le mot « marge ». Cela ne
change pas la règle, cela la précise :

> **La question « quelle est la marge sur la REF-8842 ? » *nomme* une marge, elle n'en
> *contient* aucune.** Journaliser l'entrée, c'est enregistrer ce qui a été demandé — la
> preuve même qu'E5 réclame. Journaliser la sortie, ce serait recopier `marge_ht` dans un
> fichier qu'aucune matrice d'accès ne protège.

Ce qui suit la même règle :

- **`sql` est journalisé** — il porte des noms de colonnes, et parfois un littéral
  d'identifiant dans un `WHERE` ; c'est de l'entrée reformulée, pas un résultat. Sans lui,
  aucun refus `perimetre_interdit` n'est réexaminable ;
- **`n_rows` sans les lignes** — le volume suffit à repérer une extraction massive ;
- **`citations` en clair** — ce sont des références de documents, l'objet même de la
  garantie E1 ; leur contenu n'y est pas.

Un journal qui recopierait les résultats contournerait la gouvernance qu'il est censé
prouver. C'est le seul endroit du système où une fuite serait à la fois totale et
invisible : personne ne relit un fichier de log au travers d'une matrice d'accès.

## 10. Ce que le journal doit pouvoir répondre

Les quatre tests d'acceptance MCP, rattachés au champ qui les prouve :

| Test d'acceptance | Ce qui le prouve dans le journal |
|---|---|
| le client n'accède qu'aux tools, collections et tables prévus | `profil` + `tool` + `etage` + `n_rows` |
| un client non autorisé est refusé avec un message clair **et journalisé** | `decision: denied` + `code: tool_interdit` + `etage: entree_serveur` |
| `search_docs` puis `get_document` fonctionnent séparément | deux lignes, deux `tool`, `code: ok` |
| une session de démonstration : **tous** les appels y figurent | une ligne par appel, sans exception — y compris `hors_corpus` et `aucune_ligne` |

## 11. Ce que ce document corrige

1. **le premier jet ne disait pas la forme MCP du refus** — il décrivait le contenu, pas le
   véhicule ; `isError` contre erreur de protocole est tranché ici (§1) ;
2. **les codes anglais de Q3 sont abandonnés**, et `colonne_interdite` absorbé dans
   `perimetre_interdit` — les quatre fichiers concernés du chantier 2 et Q3 sont corrigés (§7) ;
3. **le premier jet listait `erreur_execution` parmi les refus** ; il porte `isError` mais
   n'en est pas un, et la distinction est maintenant explicite (§4) ;
4. **un champ manquait au journal de l'archive** : `etage`, sans lequel la défense en
   profondeur n'est pas lisible (§8).

## 12. Reproduction

```bash
# Jeu SQL — types transcrits en ../2-text-to-sql/description-base.md §8
# attendu : 2 ambigue · 4 ecriture · 2 hors_schema · 12 metier · 4 table_interdite
grep -oE '\| (metier|ecriture|table_interdite|hors_schema|ambigue) \|' \
  2-text-to-sql/description-base.md | sort | uniq -c
```

**Jeu RAG** — 30 questions, **8 `reference_exacte`** (RAG-01 → 08), **14 `couverte`**
(RAG-09 → 22), **8 `hors_corpus`** (RAG-23 → 30), transcrites et confrontées au corpus en
[../1-rag-avance/description-corpus.md](../1-rag-avance/description-corpus.md) §7 (le
`.jsonl` reste absent du dossier livré).

Deux mesures de ce §7 comptent ici : **les huit sujets `hors_corpus` n'apparaissent dans
aucun des 400 documents**, ce qui rend le code `hors_corpus` franchement exercé ; et **les
huit références attendues existent toutes**, ce qui confirme que rien ne teste `introuvable`.

**Couverture des douze codes par les jeux fournis :**

| Statut | Codes |
|---|---|
| exercés par le jeu SQL | `ecriture_refusee` (4) · `perimetre_interdit` (4) · `hors_schema` (2) · `clarification` (2) · `ambiguite_donnees` (SQL-10, 12, 18) · `aucune_ligne` (SQL-08) |
| exercés par le jeu RAG | `hors_corpus` (8) · `ok` (22) |
| exercé par un test d'acceptance seulement | `tool_interdit` |
| **exercés par rien** | `contexte_insuffisant` · `introuvable` · `erreur_execution` |

Les trois derniers demandent des cas de test écrits par nous. **`introuvable` est le plus
exposé** : c'est le cas le plus banal en production — un client tape une référence de
travers — et le seul des trois qu'aucun jeu ne frôle.
