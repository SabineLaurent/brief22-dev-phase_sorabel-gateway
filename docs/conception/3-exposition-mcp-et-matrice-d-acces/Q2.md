# Q2 — Décrire les tools pour que le LLM du client choisisse le bon

> **Question du brief.** « Côté données : le tool génératif `ask_database`, l'outil d'aide
> `get_schema`, et les tools figés (`check_stock`, `order_status`) — comment les décrire
> pour que les clients (et leurs LLM) choisissent le bon ? »
>
> Prolonge la section « Qui choisit le tool ? » de
> [../2-text-to-sql/catalogue-tools.md](../2-text-to-sql/catalogue-tools.md), où est établi
> que les tools sont *model-controlled* (spéc. MCP **2026-07-28**, §« User Interaction
> Model ») et que **la rédaction des descriptions est le seul levier du serveur sur
> l'aiguillage**.

**Décision : une description n'est pas de la documentation, c'est une aide à la décision
écrite pour un lecteur qui n'a que ça — et elle ne s'écrit pas dans l'absolu, elle s'écrit
contre le tool voisin qu'on risque de lui préférer.**

Un LLM ne lit pas huit descriptions pour élire la meilleure : il s'arrête sur la première
qui ressemble à la question. Décrire un tool « correctement » ne sert donc à rien ; il faut
décrire ce qui le **sépare** de son voisin.

## 1. La description n'est qu'un champ sur cinq

Ce qu'un client reçoit par `tools/list`, pour chaque tool :

| Champ | Rôle dans le choix | Qui le lit |
|---|---|---|
| `name` | pèse le plus — c'est le premier signal | le LLM |
| `title` | libellé lisible, sans contrainte de nommage | l'humain, et le LLM |
| `description` | le *quand* et le *quand pas* | le LLM |
| `inputSchema` | contraint la forme de l'appel | le LLM **et** le client, qui peut valider avant d'appeler |
| `annotations` | `readOnlyHint`, `idempotentHint`, `openWorldHint` | le LLM, à titre indicatif |

**Conséquence pratique : une partie du travail de désambiguïsation se fait dans le schéma,
pas dans la phrase.** `"pattern": "^REF-\\d{4}$"` écarte un libellé de produit plus sûrement
que trois lignes de prose lui demandant de n'envoyer qu'une référence.

## 2. Les noms sont imposés, et deux d'entre eux sont des synonymes

Les tests d'acceptance nomment les huit tools : on ne les renomme pas. Or en langue
naturelle, **`answer_question` et `ask_database` disent la même chose** — « poser une
question ». Le signal le plus fort du catalogue est donc son point le plus ambigu.

Parade, puisque le nom est verrouillé : le `title` et **la première phrase** de la
description portent le domaine, jamais le verbe.

| Tool | `title` | Premiers mots de la description |
|---|---|---|
| `answer_question` | Réponse documentaire sourcée | « **Documentation produit et procédures.** Répond… » |
| `ask_database` | Interrogation de la base métier | « **Base de données commerciale.** Traduit une question… » |

## 3. Écrire contre la paire : les six collisions réelles

| Paire confusable | Discriminant à écrire | Coût si on ne l'écrit pas |
|---|---|---|
| `check_stock` ↔ `ask_database` | « stock d'**une** référence, entrepôt par entrepôt » | du SQL généré là où une requête figée suffisait, et une réponse agrégée fausse pour les 114 références présentes dans plusieurs entrepôts |
| `order_status` ↔ `ask_database` | « en-tête d'**une** commande identifiée » | idem, et le détail des lignes attendu à tort |
| `answer_question` ↔ `ask_database` | **texte** de documentation vs **chiffres** de la base | le mode d'échec le plus coûteux — voir §4 |
| `answer_question` ↔ `search_docs` | réponse rédigée + citations vs chunks bruts à composer soi-même | un client qui voulait composer reçoit de la prose ; un client qui voulait une réponse reçoit des extraits sans garantie E1 |
| `search_docs` ↔ `get_document` | recherche par similarité vs **adressage explicite par clé de document et version** — pas par référence produit : les 90 procédures SAV n'en portent aucune ([../1-rag-avance/Q1.md](../1-rag-avance/Q1.md) §8) | l'édition antérieure reste inatteignable (50 documents à deux éditions) |
| `get_schema` ↔ `ask_database` | connaître le périmètre vs obtenir un résultat | une génération déclenchée pour une question qui n'en demandait pas |

**Règle de rédaction : chaque description nomme explicitement le tool auquel céder la
main.** « Pour une question sur une procédure ou une notice, utiliser `answer_question`. »
Un LLM corrige mieux sur une consigne positive nommant une cible que sur une interdiction.

## 4. Le discriminant transverse : la forme de la question, pas son sujet

La collision `answer_question` ↔ `ask_database` ne se règle pas par le vocabulaire métier,
parce que les deux mondes parlent des mêmes objets. Les procédures SAV du corpus couvrent
`demande-duplicata-facture`, `erreur-livraison`, `mise-a-jour-adresse-livraison` — trois
sujets qui *sonnent* comme des questions de données.

| Question | Bon tool | Pourquoi |
|---|---|---|
| « Où en est la commande CMD-2025-0100 ? » | `order_status` | un identifiant bien formé désigne **un cas particulier** |
| « Que faire si je n'ai pas reçu la bonne référence ? » | `answer_question` | un **comment faire**, sans cas particulier |
| « Quelle est la garantie de REF-8842 ? » | `answer_question` | aucune colonne `garantie` n'existe dans la base ; l'information est dans les procédures SAV (« 2 ans par défaut ») |
| « Combien de commandes en avril ? » | `ask_database` | agrégat, aucun identifiant, aucun texte à citer |

> **Un identifiant bien formé oriente vers les données ; un « comment » ou un « pourquoi »
> oriente vers la documentation. Le sujet, lui, ne discrimine rien.**

Le troisième cas est le plus instructif : il montre qu'une question sur un produit
identifié n'est pas pour autant une question de base de données. C'est le contenu attendu —
un texte à citer — qui tranche, pas la présence de `REF-8842`.

## 5. Un nom de produit n'est jamais une entrée valide

**Fait mesuré sur `data/sorabel.db` : 120 références pour 52 noms distincts**, et plusieurs
libellés portés par trois références :

```
Visseuse sans fil 12 V              → 3 références
Visseuse plaquiste 550 W            → 3 références
Tableau électrique 4 rangées        → 3 références
```

Une description qui accepterait « le stock de la visseuse sans fil 12 V » forcerait le tool
à **choisir en silence** parmi trois produits. Le schéma l'interdit avant même l'appel :

```json
{
  "name": "check_stock",
  "title": "Stock d'une référence par entrepôt",
  "description": "Quantités en stock d'UNE référence produit, entrepôt par entrepôt, avec seuil de réapprovisionnement. N'accepte pas un nom de produit : 52 libellés couvrent 120 références. Pour retrouver la référence à partir d'un libellé, utiliser d'abord search_docs. Pour un agrégat sur plusieurs références, utiliser ask_database.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "ref": { "type": "string", "pattern": "^REF-\\d{4}$", "description": "ex. REF-8842" }
    },
    "required": ["ref"]
  },
  "annotations": { "readOnlyHint": true, "idempotentHint": true }
}
```

Le `pattern` a un effet que la phrase n'a pas : **beaucoup de clients valident les arguments
avant l'envoi**. L'appel fautif n'est pas refusé par le serveur, il n'a pas lieu — un
aller-retour et une entrée de journal en moins.

## 6. `readOnlyHint` informe le choix, il ne garantit rien

Les huit tools portent `readOnlyHint: true` : c'est la déclaration lisible par machine de
E3, et elle change le comportement de certains clients, qui n'exigent une confirmation
humaine que pour les tools non annotés.

**Mais la spéc MCP est explicite : les annotations sont des *hints*, un client ne doit pas
s'y fier pour décider de la sûreté d'un appel.** Elles sont fournies par le serveur, donc
non vérifiables par celui qui les lit.

> **L'annotation dit ce que le serveur promet ; la barrière est ce qu'il applique.**

La garantie reste où le chantier 2 l'a mise : validation d'AST (`N4`) et connexion
`mode=ro` + `query_only` (`N6`). Une annotation retirée ne change rien à la sécurité ; une
annotation ajoutée à tort ne l'affaiblit pas non plus. Elles n'appartiennent pas à la même
couche.

## 7. La description et le refus doivent se répondre

Le chantier 2 a prévu que chaque refus porte `{code, message, hint}`, le `hint` nommant le
tool ou la reformulation appropriée. **Ce `hint` doit citer exactement le tool nommé dans la
description du tool appelé** — sinon le LLM du client reçoit deux conseils différents pour
la même erreur et réessaie à l'identique.

```
description de ask_database : « … pour une notice ou une procédure, utiliser answer_question »
refus hors_schema           : hint = "answer_question"
```

Une seule table de correspondance `(tool, situation) → tool conseillé`, lue par les deux.
Écrire les descriptions à la main et les hints ailleurs garantit la divergence.

## 8. Le catalogue listé est filtré par profil — mais le refus reste nécessaire

Un tool interdit au profil **n'apparaît pas** dans son `tools/list`. Sans ce filtrage, le
LLM du client choisirait des tools qu'il ne peut pas appeler et récolterait des refus en
boucle : la matrice deviendrait une source d'échecs au lieu d'une frontière.

Cela ne dispense **pas** du contrôle à l'appel : rien n'empêche un client d'invoquer un nom
de tool qu'il n'a pas listé, et le test d'acceptance « client non autorisé sur un tool →
refus clair et journalisé » l'exige explicitement.

> **Le filtrage du listing est de l'ergonomie ; le refus à l'appel est la garantie.**
> Les deux lisent la même matrice (Q3).

## 9. Contrainte de format : huit descriptions dans chaque contexte client

Les descriptions sont envoyées au LLM du client **à chaque requête**. Elles se paient en
tokens et en attention. Le format retenu, quatre éléments et rien de plus :

1. **ce que le tool renvoie**, en une phrase — le résultat, pas le mécanisme ;
2. **la garantie**, énoncée telle quelle (« lecture seule », « cite toujours ses sources ») ;
3. **quand ne pas l'utiliser**, en nommant le tool voisin ;
4. **un exemple d'appel**, quand la forme de l'entrée n'est pas évidente.

Ce qu'on n'écrit pas : comment le tool fonctionne à l'intérieur (rerank, validation d'AST,
jointures). Le LLM du client n'a aucune décision à en tirer.

## 10. Ce que ce document ajoute au premier jet

`docs/archives/03-chantier-mcp.md` posait quatre règles de rédaction, toutes conservées.
Trois manques :

1. il traitait la description comme le seul support — l'essentiel de la contrainte vit dans
   `inputSchema` et dans le `name` (§1, §5) ;
2. il ne nommait aucune paire confusable, alors que c'est contre elles qu'on écrit (§3) ;
3. il ne disait pas que le catalogue listé est filtré par profil, ni pourquoi cela ne
   remplace pas le refus (§8).
