# Q3 — Restreindre le périmètre de tables et de colonnes par profil (E5)

> **Question du brief.** « Comment restreindre le périmètre de tables et de colonnes par
> profil (le support ne voit jamais prix d'achat ni marges — E5) ? »
>
> Les cinq faits de ce document sont **mesurés** sur `data/sorabel.db` et reproductibles
> par le script du §8. La partie `sqlglot` a été vérifiée en environnement isolé
> (sqlglot 30.17.0) : **la dépendance n'est pas encore déclarée dans le projet.**

**Décision : une liste blanche `profil × (table, colonne)`, contrôlée sur *toute occurrence*
d'une colonne dans l'arbre syntaxique — pas sur la seule liste de projection — appliquée à
deux endroits : en amont, pour construire le DDL filtré donné au modèle (Q1) ; en aval,
comme contrôle n° 5 de la validation AST (Q2).**

Liste blanche et non liste noire : une colonne ajoutée par une migration future doit être
**refusée** par défaut, pas exposée par défaut. Une liste noire fait le contraire.

## 1. Filtrer ce qui est affiché ne protège rien

```sql
SELECT ref, nom FROM produits ORDER BY marge_pct DESC LIMIT 3;
-- REF-8528 · REF-5603 · REF-8904
```

Aucune colonne interdite n'est projetée, et c'est **exactement la réponse à SQL-19**
(« classement des produits par marge »), la question que le jeu d'évaluation attend en
refus pour le profil support.

Le `WHERE` fuit non seulement l'ordre, mais la valeur. Par dichotomie sur
`marge_pct > ?`, **11 requêtes** suffisent à encadrer la marge de `REF-8842` dans
`[47,27 ; 47,31]` — la valeur réelle est **47,3**. Chaque requête ne renvoie qu'un booléen ;
aucune n'affiche la colonne.

**Conséquence : le contrôle porte sur `SELECT`, `WHERE`, `ORDER BY`, `GROUP BY`, `HAVING`,
`JOIN … ON` et toute sous-requête ou CTE.** Une colonne interdite n'est pas une colonne
qu'on n'affiche pas : c'est une colonne qu'on ne mentionne pas.

## 2. Les trois colonnes sensibles sont un seul secret en trois exemplaires

| Dérivation | Vérifiée sur |
|---|---:|
| `marge_pct = (prix_vente_ht − prix_achat_ht) / prix_vente_ht × 100` | **120 / 120** produits |
| `prix_achat_ht = prix_unitaire_ht − marge_ht / quantite` | **993 / 993** lignes de vente |

Les deux relations sont exactes, pas approchées. Autoriser une seule des trois colonnes
rouvre donc les deux autres par un calcul d'école.

**La matrice doit être fermée par dérivation** : avant de trancher une colonne, on cherche
les combinaisons de colonnes autorisées qui la reconstituent. Le filtrage est colonne par
colonne, mais il ne se *raisonne* pas colonne par colonne.

Cette fermeture tranche les deux cas laissés ouverts au §6 de
[description-base.md](description-base.md) :

- **`ventes.remise_pct` reste autorisée.** Je la soupçonnais de permettre de reconstituer
  une marge ; la mesure dit non — `marge_ht` ne vaut
  `quantite × prix_unitaire_ht × marge_pct/100` que sur **226 lignes sur 993**, et
  `remise_pct` (0 · 5 · 10) ne suffit pas à combler l'écart. Une remise dit ce qu'on a
  concédé au client, pas ce qu'on gagne ;
- **`clients.email` sort de E5.** Le motif n'est pas la confidentialité commerciale mais la
  donnée personnelle. Décision : fermée aux deux profils par défaut, ouverte sur besoin
  explicite, et **journalisée sous un motif distinct** — sans quoi un audit RGPD et un
  audit E5 lisent le même compteur.

## 3. « Table interdite » est un mauvais nom, et le jeu d'évaluation le porte

Les quatre questions du profil support (SQL-17 à SQL-20) sont typées `table_interdite`.
Le terme induit en erreur : **interdire la table `produits` au support casserait SQL-02**
(« stock total de la REF-8842 ») **et le tool `check_stock`**, qui ont tous deux besoin de
`produits.ref` et `produits.nom`.

La granularité est **la colonne**. `produits` reste ouverte au support, amputée de
**2 colonnes sur 9**.

### La matrice, en clair

| Table | Colonnes | commercial | support |
|---|---|---|---|
| `produits` | `ref` `nom` `categorie` `fabricant` `unite` `prix_vente_ht` `actif` | ✅ | ✅ |
| `produits` | **`prix_achat_ht`** · **`marge_pct`** | ✅ | ⛔ |
| `ventes` | `commande_id` `ref` `quantite` `prix_unitaire_ht` `remise_pct` | ✅ | ✅ |
| `ventes` | **`marge_ht`** | ✅ | ⛔ |
| `clients` | `id` `raison_sociale` `segment` `ville` | ✅ | ✅ |
| `clients` | **`email`** | ⛔ | ⛔ |
| `stocks` · `commandes` | toutes | ✅ | ✅ |

**Décision à assumer : le commercial voit les marges et le prix d'achat.** E5 ne nomme que
le support (« les colonnes sensibles ne sortent jamais pour le profil support ») et le jeu
d'évaluation ne comporte aucune question commerciale sur ces colonnes. C'est le sens
littéral de l'exigence, et c'est réversible : la matrice est une donnée de configuration,
pas du code.

## 4. `SELECT *` n'est pas à interdire, il est à développer

`SELECT * FROM produits` expose 9 colonnes, dont 2 interdites au support. L'étoile
contourne le DDL filtré donné au modèle : le schéma en amont ne mentionne pas
`marge_pct`, l'étoile la ramène quand même.

`sqlglot.optimizer.qualify`, alimenté par le schéma réel lu en `PRAGMA table_info`,
**développe l'étoile avant le contrôle** — vérifié : les 9 colonnes de `produits`
apparaissent nommément dans l'arbre. `*` devient donc un cas ordinaire, sans règle
spéciale, et le refus tombe sur les deux colonnes fautives.

**Le refus nomme la colonne au lieu de réécrire la requête en silence.** Une requête
amputée de ses colonnes interdites s'exécute et renvoie un résultat que l'utilisateur croit
complet — c'est le mode d'échec que tout ce chantier cherche à éviter. Contrepartie
assumée : le message de refus apprend au support que `marge_pct` existe. Un nom de colonne
est un moindre mal comparé à un chiffre faux non signalé.

## 5. Le piège d'implémentation : un alias de table contourne le contrôle naïf

Comparer directement `(col.table, col.name)` à la matrice **laisse passer** ceci :

```sql
SELECT p.nom, SUM(v.marge_ht) FROM ventes v JOIN produits p ON p.ref = v.ref GROUP BY 1;
```

`qualify` préfixe la colonne par l'alias : l'arbre porte `("v", "marge_ht")`, et
`("v","marge_ht") ∉ interdits`. **Un alias d'une lettre suffit à sortir les marges.**

La parade, vérifiée dans les deux sens : parcourir les *scopes* (`build_scope`), résoudre
alias → nom réel de table dans chaque scope, puis comparer. La même requête devient un
refus `("ventes","marge_ht")` ; une requête licite (`produits p JOIN stocks s`) reste
autorisée ; et une colonne interdite cachée dans une CTE est vue dans le scope de la CTE.

C'est le genre de détail qui décide si une barrière existe ou non : la conception dit
« filtrage par colonne », l'implémentation naïve n'en applique aucun.

## 6. Où le contrôle s'applique — deux endroits, deux rôles

| | Rôle | Ce qui se passe s'il manque |
|---|---|---|
| **Amont** — DDL filtré (Q1) | le modèle ne peut pas générer ce qu'il ne voit pas | le modèle produit du SQL correct qui sera refusé en aval : refus fréquents, expérience dégradée |
| **Aval** — contrôle n° 5 de l'AST (Q2) | la garantie | un modèle qui hallucine `marge_pct`, ou un client qui envoie du SQL sans passer par la génération, atteint les données |

L'amont est une **aide**, l'aval est la **barrière**. Les deux lisent la même matrice, et
la même fonction la construit : un DDL filtré qui divergerait de la règle de validation
produirait des refus incompréhensibles.

Le troisième étage — la matrice `client × tool` à l'entrée du serveur MCP — relève du
chantier 3.

## 7. Ce que ce document corrige du premier jet

`docs/archives/02-chantier-text-to-sql.md` posait une matrice *profil × colonne* sans dire
où le contrôle s'applique dans la requête. Trois ajouts issus des mesures :

- la projection n'est pas le lieu du contrôle (§1) — le premier jet raisonnait « colonnes
  renvoyées » ;
- `produits.marge_pct` manquait du radar : SQL-19 se répond **sans toucher `ventes`** ;
- `ventes.remise_pct` était soupçonnée à tort, `clients.email` était rangée sous E5 alors
  que son motif est autre (§2).

## 8. Reproduction

```python
import sqlite3
c = sqlite3.connect("file:data/sorabel.db?mode=ro", uri=True)

# §1 — SQL-19 repondue sans projeter marge_pct
c.execute("SELECT ref, nom FROM produits ORDER BY marge_pct DESC LIMIT 3").fetchall()

# §1 — 11 requetes booleennes suffisent a retrouver la marge de REF-8842
lo, hi, n = 0.0, 100.0, 0
while hi - lo > 0.05:
    mid, n = (lo + hi) / 2, n + 1
    hit = c.execute("SELECT 1 FROM produits WHERE ref='REF-8842' AND marge_pct > ?", (mid,)).fetchone()
    lo, hi = (mid, hi) if hit else (lo, mid)
print(n, lo, hi)          # 11  47.27  47.31   (valeur reelle 47.3)

# §2 — les deux derivations, exactes
q = c.execute("SELECT prix_vente_ht, prix_achat_ht, marge_pct FROM produits").fetchall()
sum(abs((v - a) / v * 100 - m) < 0.05 for v, a, m in q)                       # 120 / 120

r = c.execute("""SELECT v.quantite, v.prix_unitaire_ht, v.marge_ht, p.prix_achat_ht
                   FROM ventes v JOIN produits p ON p.ref = v.ref""").fetchall()
sum(abs((pu - m / q_) - pa) < 0.5 for q_, pu, m, pa in r)                     # 993 / 993
```

```python
# §4 et §5 — controle par l'AST, alias resolus par scope   (pip install sqlglot)
import sqlglot
from sqlglot import exp
from sqlglot.optimizer.qualify import qualify
from sqlglot.optimizer.scope import build_scope

schema = {t: {r[1]: r[2] for r in c.execute(f"PRAGMA table_info({t})")}
          for t in ("produits", "stocks", "clients", "commandes", "ventes")}
INTERDIT = {("produits", "prix_achat_ht"), ("produits", "marge_pct"), ("ventes", "marge_ht")}

def colonnes_reelles(sql):
    arbre = qualify(sqlglot.parse_one(sql, dialect="sqlite"), schema=schema, dialect="sqlite")
    vues = set()
    for scope in build_scope(arbre).traverse():
        sources = {nom: src.name for nom, src in scope.sources.items() if isinstance(src, exp.Table)}
        for col in scope.expression.find_all(exp.Column):
            vues.add((sources.get(col.table, col.table), col.name))
    return vues

def refus(sql):
    return sorted(colonnes_reelles(sql) & INTERDIT)

refus("SELECT * FROM produits LIMIT 5")
# -> [('produits','marge_pct'), ('produits','prix_achat_ht')]        etoile developpee

refus("SELECT p.nom, SUM(v.marge_ht) FROM ventes v JOIN produits p ON p.ref=v.ref GROUP BY 1")
# -> [('ventes','marge_ht')]        sans build_scope : liste vide, la requete passait

refus("WITH t AS (SELECT ref, marge_pct FROM produits) SELECT ref FROM t ORDER BY marge_pct DESC")
# -> [('produits','marge_pct')]     vue dans le scope de la CTE

refus("SELECT p.nom FROM produits p JOIN stocks s ON s.ref=p.ref WHERE s.entrepot='LYON'")
# -> []                             requete licite, non bloquee
```
