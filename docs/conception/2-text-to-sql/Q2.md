# Q2 — Garantir la lecture seule (E3)

> **Question du brief.** « Comment garantir la lecture seule (E3) : droits au niveau de la
> connexion, validation de la requête générée (liste de mots interdits, analyse), `LIMIT`
> par défaut ? **Une seule barrière suffit-elle ?** »
>
> Tous les résultats de ce document sont **mesurés** sur `data/sorabel.db`
> (SQLite 3.51.0) ; les tests sont reproductibles par le script du §6.

**Réponse directe : non, une seule barrière ne suffit pas — et pas par principe de
précaution. Chaque barrière prise seule a un contournement mesuré dans ce dépôt.**

**Décision : quatre couches, dont trois portent sur un risque qu'aucune des autres ne
couvre.**

## 1. Ce que les tests montrent

Trois configurations de connexion, six tentatives. `mode=ro` désigne l'ouverture
`file:sorabel.db?mode=ro` ; `query_only` le `PRAGMA query_only=ON`.

| Tentative | `mode=ro` seul | `query_only` seul | les deux |
|---|---|---|---|
| `UPDATE` · `DELETE` · `CREATE TABLE` | refusé | refusé | refusé |
| deux instructions séparées par `;` | refusé **par le driver** | refusé | refusé |
| `ATTACH` puis `CREATE TABLE p.vol AS SELECT * FROM produits` | **PASSE — 120 lignes copiées** | refusé | refusé |
| `VACUUM INTO 'copie.db'` | **PASSE — 156 Ko, base entière** | refusé | refusé |
| `PRAGMA query_only=OFF` puis `UPDATE` | sans effet (fichier `ro`) | **PASSE — l'état se désactive** | fichier protégé, mais la fuite redevient possible |
| `ATTACH DATABASE` seul | passe | passe | **passe** |

Cinq conclusions, chacune tirée d'une ligne :

**1.1 — `mode=ro` protège le fichier, pas les données.** Deux instructions suffisent à en
sortir une copie complète, `prix_achat_ht` et `marge_pct` compris. La copie exfiltrée est
lisible : `SELECT prix_achat_ht, marge_pct FROM produits` y renvoie `(101.03, 47.3)`. Le
premier jet ne voyait que le risque d'écriture ; **le risque symétrique est la fuite**, et
il traverse toutes les barrières pensées pour « empêcher d'écrire dans la base ».

**1.2 — `query_only=ON` protège la connexion, mais ce n'est pas une barrière : c'est un
état.** Il bloque `UPDATE`, `CREATE … AS SELECT` vers une base attachée et `VACUUM INTO` —
strictement plus que `mode=ro`. Mais `PRAGMA query_only=OFF` **passe**, et l'écriture
redevient possible derrière. Une protection qu'une requête peut retirer ne compte pas
comme garantie.

**1.3 — Les deux ensemble ne laissent passer que `ATTACH` seul.** Attacher sans pouvoir
écrire ne fait fuir aucune donnée, mais permet d'**ouvrir un autre fichier et de le lire**
— donc de contourner le filtrage de tables du profil si une copie non filtrée existe
quelque part. `ATTACH` reste à refuser.

**1.4 — Le trou combiné, et il est structurel.** Sur une connexion **réutilisée** entre
deux appels du tool : appel 1 `PRAGMA query_only=OFF`, appel 2 `VACUUM INTO`. Chaque appel
est une instruction unique, aucune n'écrit dans la base source. D'où une décision
d'implémentation, pas de confort : **connexion neuve par requête**, `query_only` réarmé à
chaque ouverture.

**1.5 — Le driver Python offre une barrière gratuite.** `cursor.execute()` refuse les
instructions multiples : « You can only execute one statement at a time ». L'injection de
second ordre après `;` — le scénario classique — meurt avant d'atteindre le validateur.
À **nommer** dans la conception plutôt qu'à reconstruire.

## 2. Pourquoi la liste de mots interdits est définitivement écartée

```sql
VACUUM INTO '/tmp/copie.db';
```

Une instruction. Elle sort les 156 Ko de la base — les cinq tables, toutes les colonnes,
y compris celles interdites au support. Elle ne contient **ni `INSERT`, ni `UPDATE`, ni
`DELETE`, ni `DROP`, ni `TRUNCATE`**.

Une liste noire énumère des **mots** quand le danger est une **opération**. Elle ne peut
pas être complète : il faudrait y avoir pensé d'avance. L'analyse de l'arbre syntaxique
pose la bonne question — *quel type de nœud est la racine, quelles tables et colonnes sont
réellement référencées* — au lieu de chercher des sous-chaînes dans du texte.

## 3. Les quatre couches retenues

### C1 — Les permissions du fichier sur le disque

`chmod 444` sur `sorabel.db`, ou un propriétaire distinct de l'utilisateur qui exécute le
serveur.

**C'est la seule barrière hors de portée du code applicatif.** Sous PostgreSQL, la
gouvernance des droits vit dans la base (`CREATE ROLE`, `GRANT SELECT`). SQLite n'a ni
utilisateurs, ni rôles, ni `GRANT` : **sous SQLite, cette gouvernance vit dans le système
de fichiers.** Ce n'est pas un pis-aller, c'est l'endroit équivalent.

Ce que C1 ne couvre pas : la lecture. Un fichier lisible reste exfiltrable.

### C2 — La connexion : `mode=ro` **et** `PRAGMA query_only=ON`, neuve à chaque requête

Les deux, parce que chacun couvre le contournement de l'autre (§1.1 et §1.2). Neuve à
chaque requête, à cause du §1.4.

Ce que C2 ne couvre pas : elle refuse, mais avec un message SQLite (`attempt to write a
readonly database`) indistinguable d'un bug d'infrastructure. Le test d'acceptance exige
un refus **journalisé et clair** ; C2 ne le fournit pas.

### C3 — La validation de l'arbre syntaxique (`sqlglot`)

Cinq contrôles :

1. **une seule instruction** ;
2. **racine `SELECT` ou `WITH … SELECT`** ;
3. **aucun nœud de modification** dans tout l'arbre — y compris dans une sous-requête ou
   une CTE ;
4. **aucun `PRAGMA`, `ATTACH`, `DETACH`, `VACUUM`** — les quatre que la connexion laisse
   passer ou dont elle dépend ;
5. **toutes les tables et colonnes référencées ∈ matrice(profil)** — traité en Q3.

**C'est la seule couche qui produise un refus lisible, motivé et journalisable.** C'est
donc elle qui satisfait le test d'acceptance « la demande est refusée (lecture seule) et
journalisée », pas la connexion.

### C4 — Les bornes d'exécution : `LIMIT` injecté, plafond de lignes, timeout

- **`LIMIT` injecté** s'il est absent, jamais en remplacement d'un `LIMIT` plus petit déjà
  présent ;
- **plafond de lignes ramenées** côté client, indépendant du `LIMIT` ;
- **timeout**, par `set_progress_handler` (rappel appelé toutes *n* instructions de la
  machine virtuelle, qui interrompt en renvoyant une valeur non nulle) ou par
  `interrupt()` depuis un thread minuteur. **Les deux ont été vérifiés** : interruption à
  0,50 s et à 0,06 s respectivement, avec `OperationalError: interrupted`. SQLite n'a pas
  de `statement_timeout` — sans l'un de ces deux mécanismes, la décision « timeout » ne
  serait pas implémentable.

**Une nuance mesurée, à ne pas cacher.** Sur cette base de 156 Ko, un produit cartésien de
**40,5 millions de lignes** (`FROM ventes, commandes, produits`) se calcule en **0,4 s**.
Le risque immédiat n'est donc pas le temps de calcul mais le **volume ramené** :
`SELECT * FROM ventes, commandes` renvoie **337 620 lignes** au client. Ici, le `LIMIT`
compte plus que le timeout ; le timeout est la garantie de bord pour une base qui
grossira.

Sur l'incident fondateur du brief — « une commerciale a verrouillé la base un vendredi
soir » : `journal_mode` vaut **`delete`**, pas `wal`. Sous ce mode, un lecteur prend un
verrou partagé qui **bloque les écrivains**. Le scénario est donc reproductible, et C4 est
la seule couche qui le traite. Passer la base en `wal` supprimerait ce blocage, mais c'est
une modification de la base : hors du périmètre d'un accès en lecture seule, et à proposer
séparément.

## 4. Répartition des risques — la justification des quatre couches

| Risque | C1 fichier | C2 connexion | C3 AST | C4 bornes |
|---|---|---|---|---|
| écriture dans la base | ✅ | ✅ | ✅ | |
| exfiltration par `ATTACH` / `VACUUM INTO` | | ✅ (`query_only`) | ✅ | |
| lecture hors périmètre du profil | | | ✅ | |
| refus lisible et journalisable | | | ✅ | |
| saturation (volume, verrou, temps) | | | | ✅ |
| bug du code applicatif lui-même | ✅ | | | |

**Aucune colonne ne couvre toutes les lignes.** C'est la réponse à la question du brief.

## 5. Ce que ce document corrige du premier jet

`docs/archives/02-chantier-text-to-sql.md` §3 classait `mode=ro` en « solide mais
applicatif ». Deux corrections :

- ce n'est pas « applicatif » : c'est le **handle SQLite** qui refuse l'écriture, pas une
  convention de code. Ce qui échappe au code, en revanche, c'est **C1** — les permissions
  du fichier — que le premier jet ne mentionnait pas ;
- le premier jet raisonnait **écriture** ; les tests montrent que le chemin réellement
  ouvert est **la fuite**. Un `VACUUM INTO` fait sortir la base entière sans écrire une
  ligne dedans.

## 6. Reproduction

```python
import sqlite3, os
db = os.path.abspath('data/sorabel.db')

# §1.1 — mode=ro n'empeche pas l'exfiltration
c = sqlite3.connect(f"file:{db}?mode=ro", uri=True)
c.execute("ATTACH DATABASE '/tmp/exfil.db' AS p")           # PASSE
c.execute("CREATE TABLE p.vol AS SELECT * FROM produits")    # PASSE -> 120 lignes
c.close()

c = sqlite3.connect(f"file:{db}?mode=ro", uri=True, isolation_level=None)
c.execute("VACUUM INTO '/tmp/copie.db'")                     # PASSE -> 156 Ko
c.close()

# §1.2 — query_only se desactive en SQL (sur une copie ecrivable)
c = sqlite3.connect('/tmp/copie.db', isolation_level=None)
c.execute("PRAGMA query_only=ON")
c.execute("PRAGMA query_only=OFF")                           # PASSE
c.execute("UPDATE produits SET prix_vente_ht=1")             # PASSE
c.close()

# §1.3 — les deux couches ensemble
c = sqlite3.connect(f"file:{db}?mode=ro", uri=True, isolation_level=None)
c.execute("PRAGMA query_only=ON")
c.execute("VACUUM INTO '/tmp/x.db'")   # REFUSE : attempt to write a readonly database
c.close()

# §3 C4 — le timeout fonctionne
import time
c = sqlite3.connect(f"file:{db}?mode=ro", uri=True)
debut = time.monotonic()
c.set_progress_handler(lambda: 1 if time.monotonic() - debut > 0.5 else 0, 10)
c.execute("SELECT SUM(v.quantite) FROM ventes v, commandes c, produits p")
# -> OperationalError: interrupted, apres 0,50 s
```
