# Q4 — Les tools SQL figés

> **Question du brief.** « Quels besoins récurrents méritent des tools SQL figés
> (requêtes paramétrées écrites par vous : stock d'une référence, statut d'une commande)
> plutôt que du SQL généré ? Quel est l'intérêt de chaque approche ? »
>
> Tous les chiffres de ce document sont **mesurés** sur `data/sorabel.db` et
> reproductibles par le script du §7.

**Décision : deux tools figés, `check_stock(ref)` et `order_status(order_id)` — ceux que
le brief nomme, pas un de plus. Le critère de figement n'est pas la fréquence du besoin,
c'est le fait que la question ait une forme unique, un paramètre typé, et une sémantique
que le SQL généré peut se tromper à reconstituer.**

## 1. Pourquoi le critère n'est pas « c'est récurrent »

Le brief parle de besoins *récurrents*. La récurrence n'est pas mesurable dans ce projet :
il n'existe aucun journal d'usage, et le jeu d'évaluation compte **une** occurrence par
question. Figer sur une fréquence supposée revient à deviner.

Le critère mesurable est ailleurs : **la question a une seule bonne réponse, et le SQL
généré en a plusieurs plausibles.**

```
SQL-02 « stock total de la REF-8842 ? »
   première ligne de stocks : 247       SUM sur les trois entrepôts : 774
```

**114 références sur 120** sont stockées dans plus d'un entrepôt (78 dans les trois).
Sur `REF-4032`, la plus grosse ligne vaut 467 quand le total vaut 1 273. Une génération
qui oublie le `SUM` renvoie un nombre **juste pour un entrepôt et faux pour la question** —
sans erreur SQL, sans avertissement, sans rien qui le signale.

### Les trois conditions du figement, cumulatives

1. **une forme unique** — pas de variante métier légitime de la question ;
2. **un paramètre typé et vérifiable** avant exécution : `REF-\d{4}`, `CMD-\d{4}-\d{4}` ;
3. **une sémantique piégeuse**, que le figement tranche une fois pour toutes au lieu de la
   confier à chaque génération.

`check_stock` et `order_status` remplissent les trois. C'est pour cela qu'ils sont figés,
et non parce qu'on suppose qu'on les appellera souvent.

## 2. L'intérêt de chaque approche

| | Tool figé | SQL généré |
|---|---|---|
| SQL exécuté | écrit et relu **une fois** | différent à chaque appel |
| Vérification de la matrice d'accès (Q3) | **statique**, à la revue de code | à chaque requête, sur l'AST |
| Coût d'un appel | **10,7 ms pour 1000 appels** — ni LLM, ni parsing, ni validation | un appel de modèle, puis qualification et validation |
| Test d'acceptance | rejouable à l'identique | dépend de la génération du jour |
| Couverture du jeu d'évaluation | **2 questions sur 24** | les 22 autres |

Le tool figé n'est pas « la version sûre » du SQL généré : c'est ce qui reste quand une
question est stable. La valeur du généré est exactement celle que le figé n'a pas —
SQL-12 (top 3 des clients par montant) ou SQL-09 (annulées depuis janvier) ne méritent pas
un tool chacune, et personne ne peut énumérer d'avance les questions que le métier posera.

**La différence de sûreté n'est pas *si* l'on vérifie, mais *quand*.** Le figé se vérifie
une fois, à la revue ; le généré à chaque requête, par les quatre couches de Q2 et la
matrice de Q3.

## 3. Le contrat de sortie de `check_stock(ref)`

**N lignes plus un total, jamais un scalaire.**

```
REF-8842 → LILLE  247  (seuil 10)   sous_seuil = non
           LYON   100  (seuil 50)   sous_seuil = non
           NANTES 427  (seuil 20)   sous_seuil = non
           total  774
```

Les **seuils de réapprovisionnement diffèrent par entrepôt** (10 · 50 · 20 pour cette
seule référence) : « la REF-8842 est-elle sous son seuil ? » n'a pas de réponse globale.
Le tool renvoie donc `sous_seuil` **par ligne**, jamais agrégé — un booléen global serait
une information inventée.

**Le paramètre est une référence, jamais un libellé.** 120 références pour 52 noms
distincts (§5.4 de la description de la base) : un libellé n'identifie pas un produit.
Un utilisateur qui demande « le disjoncteur tétrapolaire 40 A » doit d'abord passer par
une résolution nom → références, qui lui renvoie les quatre candidats avec leurs prix.
C'est le **pont RAG ↔ SQL**, et c'est ce qui empêche `check_stock` d'être auto-suffisant.

## 4. Le contrat de sortie de `order_status(order_id)`

**L'en-tête de commande seul.**

```
CMD-2025-0042 → statut livree · 2025-11-22 · 28 524,27 € · client CLI-1015
```

Pas le détail des lignes de vente — 2,92 par commande en moyenne, jusqu'à 5. La question
posée est le statut ; le détail est un autre besoin, donc un autre tool ou du SQL généré.
Un paramètre optionnel `avec_detail` ferait deux tools dans un, avec deux lignes de
matrice d'accès différentes derrière une seule signature : c'est précisément ce que la
gouvernance par tool cherche à éviter.

## 5. Trois sorties distinctes, pour les deux tools

| Sortie | Quand | Exemple mesuré |
|---|---|---|
| **résultat** | la clé existe | `CMD-2025-0042` → `livree` |
| **aucune ligne** | la clé est bien formée mais absente | `CMD-2026-0042` (SQL-08) · `REF-9999` |
| **refus** | profil non autorisé, ou paramètre malformé | matrice de Q3 |

`CMD-2026-0042` **n'existe pas** — seule `CMD-2025-0042` existe, la numérotation étant
globale et trouée par année. Répondre « aucun résultat » est correct ; répondre « refusé »
serait faux, et c'est le comportement d'un tool qui traite l'absence comme une erreur.
Cette distinction est un livrable du tool, pas un détail d'implémentation : le client MCP
la présentera différemment à l'utilisateur dans les trois cas.

## 6. Ce que le figement ne dispense pas de faire

- **La matrice d'accès s'applique à l'identique.** Un tool figé n'est pas hors
  gouvernance : ses colonnes de sortie sont des lignes de la matrice de
  [Q3](Q3.md) §3. `check_stock` renvoie `stocks.entrepot`, `stocks.quantite`,
  `stocks.seuil_reappro` et `produits.nom` — toutes ouvertes aux deux profils.
  `order_status` renvoie `commandes.montant_ht`, ouverte au support d'après la matrice :
  **décision assumée, pas oubli.**
- **Le journal aussi** (E5) : tout appel, autorisé comme refusé, avec le profil, le tool,
  le paramètre et la sortie retenue parmi les trois du §5.
- **La validation du paramètre** reste à faire : une `ref` malformée est un refus, pas une
  requête à tenter.

## 7. Le troisième tool que je n'ajoute pas

SQL-07 (« quelles références sous seuil de réapprovisionnement à LYON ? » — 3 lignes ;
22 sur toute la base) est le meilleur candidat restant. Il remplit les trois conditions du
§1 : forme stable, paramètre typé (`entrepot ∈ {LILLE, LYON, NANTES}`), et une sémantique
qui se trompe facilement — `quantite < seuil_reappro` compare **deux colonnes**, pas une
colonne à une constante, et c'est une erreur de génération classique.

**Je le laisse au SQL généré.** Aucun test d'acceptance ne le demande, et chaque tool est
une surface de plus à décrire, gouverner, journaliser, tester et maintenir. C'est le point
le plus attaquable de cette réponse : si un besoin réel de réapprovisionnement apparaît,
c'est le premier à figer.

## 8. Reproduction

```python
import sqlite3, time
c = sqlite3.connect("file:data/sorabel.db?mode=ro", uri=True)
q = lambda s, *a: c.execute(s, a).fetchall()

# §1 — 114 refs sur 120 sont en plusieurs entrepots
q("SELECT n, COUNT(*) FROM (SELECT ref, COUNT(*) n FROM stocks GROUP BY ref) GROUP BY n")
# -> [(1, 6), (2, 36), (3, 78)]

# §1 — SQL-02 : premiere ligne 247, total 774
q("SELECT quantite FROM stocks WHERE ref='REF-8842'")[0][0]      # 247
q("SELECT SUM(quantite) FROM stocks WHERE ref='REF-8842'")[0][0] # 774

# §1 — l'ecart maximal entre une ligne et le total
q("""SELECT ref, MAX(quantite), SUM(quantite) FROM stocks GROUP BY ref
      ORDER BY SUM(quantite) - MAX(quantite) DESC LIMIT 1""")     # REF-4032, 467, 1273

# §2 — cout d'un tool fige
t = time.perf_counter()
for _ in range(1000):
    c.execute("SELECT entrepot, quantite FROM stocks WHERE ref=?", ("REF-8842",)).fetchall()
print(f"{(time.perf_counter() - t) * 1000:.1f} ms")               # ~10,7 ms

# §3 — les seuils different par entrepot
q("SELECT entrepot, quantite, seuil_reappro FROM stocks WHERE ref='REF-8842' ORDER BY entrepot")
# -> [('LILLE', 247, 10), ('LYON', 100, 50), ('NANTES', 427, 20)]

# §4 — lignes de vente par commande : 1 a 5, moyenne 2,92
q("SELECT MIN(n), ROUND(AVG(n),2), MAX(n) FROM (SELECT COUNT(*) n FROM ventes GROUP BY commande_id)")

# §5 — aucune ligne n'est pas une erreur
q("SELECT id FROM commandes WHERE id='CMD-2026-0042'")                     # []
q("SELECT * FROM stocks WHERE ref='REF-9999'")                            # []

# §7 — SQL-07 : comparaison de deux colonnes
q("SELECT COUNT(*) FROM stocks WHERE entrepot='LYON' AND quantite < seuil_reappro")  # 3
q("SELECT COUNT(*) FROM stocks WHERE quantite < seuil_reappro")                      # 22
```
