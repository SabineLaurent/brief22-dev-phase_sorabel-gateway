# Q1 — Passer d'une question métier à une requête

> **Question du brief.** « Comment passer d'une question métier à une requête : que
> donnez-vous au modèle (schéma commenté, exemples de requêtes, valeurs types) pour qu'il
> génère juste ? »
>
> Tous les faits cités sont mesurés dans [description-base.md](description-base.md).

**Décision : on ne donne pas « le schéma de la base », on donne un contrat de lecture de
la base, construit par le code depuis la matrice du profil.** Cinq blocs, et un seul
artefact qui les porte.

## 1. Le DDL filtré par profil, commenté colonne par colonne

Les conventions vivent dans les commentaires, pas dans les types.

```sql
CREATE TABLE commandes (
  id            TEXT,  -- format CMD-AAAA-NNNN ; numérotation globale, trouée par année
  client_id     TEXT,  -- → clients.id
  date_commande TEXT,  -- 'YYYY-MM-DD' ; données du 2025-09-04 au 2026-08-19
  statut        TEXT,  -- livree | expediee | annulee | en_attente | preparee (sans accents)
  montant_ht    REAL   -- montant BRUT, AVANT remise ; les remises sont dans ventes.remise_pct
);
CREATE TABLE ventes (  -- LIGNES DE COMMANDE ; ne porte AUCUNE date :
  commande_id   TEXT,  -- pour filtrer par date, joindre commandes.date_commande
  ref           TEXT,  -- → produits.ref
  quantite      INTEGER,
  prix_unitaire_ht REAL,
  remise_pct    REAL,  -- 0 | 5 | 10
  marge_ht      REAL   -- marge en euros de CETTE ligne ; sans rapport avec produits.marge_pct
);
```

**Pourquoi.** Le type d'une colonne ne dit pas ce qu'elle contient. `montant_ht REAL` est
vrai et inutile ; « montant brut, avant remise » est ce qui décide entre deux requêtes
également correctes — voir le piège §5.1 de la description de la base, où le montant
reconstitué depuis les lignes ne correspond qu'à 91 commandes sur 340 si l'on déduit les
remises, et à 340 sur 340 si on ne les déduit pas. Le commentaire est le seul endroit où
ce fait peut vivre.

## 2. Les énumérations exactes

`livree` sans accent · `LILLE` en capitales · `collectivité` accentué en minuscules :
**trois conventions différentes dans la même base**, dont aucune ne se devine.

**Pourquoi.** C'est le mode d'échec le plus vicieux du Text-to-SQL. `statut = 'livrée'`
est syntaxiquement parfait, passe la validation, est autorisé par la matrice d'accès — et
renvoie zéro ligne sans que rien ne le signale. Une réponse fausse déguisée en réponse
vide.

## 3. La plage temporelle, pas une année de référence

Les données couvrent 12 mois consécutifs, du 2025-09 au 2026-08, et **chaque mois du
calendrier n'y apparaît qu'une fois.**

**Pourquoi.** « Combien de commandes en avril ? » (SQL-01) n'est donc pas ambigu : avril
désigne 2026-04. Donner la plage suffit et ne suppose rien ; injecter une convention
« année = 2026 » supposerait un choix que les données ont déjà tranché. Sans la plage, le
modèle datera sur l'année courante et renverra zéro ligne.

## 4. Trois à cinq exemples question → SQL, choisis pour le piège qu'ils désamorcent

Un exemple ne sert pas à montrer une forme, il sert à interdire une erreur mesurée.

| Exemple | Ce qu'il empêche |
|---|---|
| marge des ventes d'un mois | l'invention de `ventes.date_vente` — la jointure `ventes → commandes` est obligatoire |
| stock d'une référence | la réponse sur une seule ligne, alors que `stocks` en porte ~2,6 par référence |
| prix d'un produit désigné par son nom | le choix silencieux d'un homonyme : `SELECT ref, nom, prix_vente_ht`, toutes les lignes |
| commandes livrées d'un mois | la valeur de statut accentuée |

## 5. Les conventions métier, énoncées comme des consignes

Elles ne sont pas dans le schéma — ce sont des choix. Sans elles, le résultat n'est pas
interprétable :

- **les commandes annulées sont exclues** des chiffres de vente, de marge et de quantité ;
- **le montant d'une commande est `montant_ht`**, brut ;
- **un produit s'identifie par sa référence** ; désigné par son nom, on renvoie tous les
  candidats.

**Décision réversible, à assumer comme telle.** Sur la première : la marge de mai 2026
vaut **113 604,48 €** hors annulées contre **154 093,48 €** toutes commandes confondues,
soit 26 % d'écart. Exclure est plus juste métier — une commande annulée n'a produit aucune
marge — mais le jeu d'évaluation a peut-être été généré sur le total. **Sans
`eval/questions_sql.jsonl`, on ne peut pas savoir laquelle des deux valeurs le test
d'acceptance attend.** D'où la parade : la convention est appliquée par défaut,
**paramétrable, et renvoyée avec le résultat.**

## Ce qu'on ne donne pas

**Pas d'échantillon de lignes.** Le brief suggère des « valeurs types » : oui pour les
colonnes à faible cardinalité, qui sont un *vocabulaire* ; non pour les valeurs de
données, qui sont du *contenu*.

**Pourquoi.** Montrer trois lignes de `produits` au profil support ferait fuiter
`prix_achat_ht` **dans le prompt lui-même** — en amont de toute génération, donc dans un
endroit que le validateur SQL ne regarde pas. La fuite ne serait pas détectable par la
barrière prévue pour l'empêcher.

## Où vit cet artefact

**Un seul objet, construit par le code depuis le schéma réel et la matrice du profil,
jamais écrit à la main.** Il sert deux consommateurs : le prompt de `ask_database`, et le
tool `get_schema` que le brief nomme déjà.

**Pourquoi.** Un prompt recopié à la main dériverait du schéma dès la première migration,
et cette dérive est silencieuse : un DDL faux dans le prompt produit du SQL faux, pas une
erreur.

## Corollaire pour la transparence (E3)

La réponse ne renvoie pas `{résultat, requête}` mais **`{résultat, requête, conventions
appliquées}`**. Un chiffre de marge sans mention du sort des commandes annulées n'est pas
vérifiable par le métier — et E3 demande la transparence, pas seulement la traçabilité.

## Renvois

- Le **schéma filtré par profil** de ce document est produit par la matrice d'accès —
  voir Q3.
- Le **format de sortie** (`{sql} | {clarification} | {refus}`) et le cas de l'ambiguïté
