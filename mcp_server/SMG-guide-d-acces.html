Sorabel MCP gateway - Guide d'accès

Page générée le 2026-09-13 par make doc-tools, depuis ce que tools/list répond réellement, profil par profil. Elle n'est pas rédigée : un argument renommé ou un tool retiré à un profil s'y voit à la régénération suivante.

Cette page se suffit à elle-même : se brancher, lire une réponse, et les huit fiches. Ce qu'elle ne porte pas — les garanties détaillées, les limites chiffrées et les écarts assumés — vit dans le guide d'intégration du dépôt.

1 · Se brancher

Le serveur parle stdio : ni port, ni URL, ni jeton. Un processus par profil, et le profil est posé par qui lance le processus — jamais par le client, jamais par le modèle.

Prérequis

Python >=3.11,<3.12, uv, et Docker — ce dernier pour la seule base vectorielle.

uv sync --extra vector        # l'extra est nécessaire : sans lui l'embedder local casse
cp .env.example .env          # aucune valeur du modèle n'est un secret
make up                       # Chroma, via docker compose, port 8002
make seed                     # génère data/sorabel.db
make ingest                   # indexe le corpus (~400 éditions)

.env n'est pas obligatoire : les 26 réglages ont tous un défaut. Il le devient pour les appels de modèle — AZURE_AI_ENDPOINT, AZURE_AI_API_KEY, LLM_CHAT_MODEL — dont dépendent answer_question (la rédaction) et ask_database (la génération SQL). Les six autres tools fonctionnent sans : la recherche et le reclassement tournent en local par défaut.

Le bloc de configuration

À coller dans la configuration de votre client MCP :

{
  "mcpServers": {
    "sorabel": {
      "command": "uv",
      "args": ["run", "python", "-m", "mcp_server.server"],
      "cwd": "/chemin/absolu/vers/brief22-dev-phase_sorabel-gateway",
      "env": {
        "SORABEL_PROFILE": "commercial",
        "TOKENIZERS_PARALLELISM": "false"
      }
    }
  }
}

cwd est obligatoire : le corpus, la base et la matrice sont résolus relativement à la racine du dépôt. TOKENIZERS_PARALLELISM n'est pas fonctionnel — il fait taire un avertissement de la bibliothèque d'embeddings qui, sinon, encombre la console du client. SORABEL_PROFILE vaut support par défaut ; un nom inconnu retombe sur default, qui n'a aucun tool — un catalogue vide est donc le symptôme d'un profil mal orthographié, pas d'une panne.

Préférez ce bloc à une commande en ligne de commande. Certains clients — l'Inspector officiel en fait partie — analysent les arguments et avalent le -m, ce qui lance python sans module : le processus lit alors le JSON-RPC sur son entrée standard et le prend pour du code. Le symptôme est un NameError: name 'true' is not defined suivi d'un délai d'attente dépassé.

Vérifier que ça répond

make serve                    # le serveur, en stdio, profil dans SORABEL_PROFILE
make client                   # un client de test : le catalogue du profil
PROFILE=commercial make client

# avec l'Inspector officiel, le bloc ci-dessus enregistré dans mon-serveur.json :
npx @modelcontextprotocol/inspector --cli \
  --config mon-serveur.json --server sorabel --method tools/list --format json

3 · Lire une réponse

Les huit tools rendent la même enveloppe, servie comme refusée. Ce qui suit est lu dans l'outputSchema que le serveur publie — c'est le texte que reçoit déjà votre client, pas une paraphrase.

Enveloppe de réponse de la gateway Sorabel. Le discriminant est « status », puis « payload.code » qui distingue les cas d'un même statut. Ne jamais rendre à l'utilisateur un payload dont la clé de charge utile est absente : c'est un refus ou une non-réponse, et il n'y a rien à afficher.

Les trois clés sont toujours présentes : status, payload, message.

CléCe que le serveur en dit
statusL'issue de l'appel. « error » : l'exécution a échoué. « hors_corpus » : le corpus ne porte pas la réponse — ce n'est pas un refus. « ok » : servi. « refused » : la gouvernance a tranché.
payloadObjet. Toujours présent : code. Les autres clés dépendent du tool — voir sa fiche — et sont absentes, jamais vides, quand il n'y a rien à mettre dedans.
messagePhrase figée choisie sur le code, destinée à l'utilisateur. Vide sur « ok », non vide sur tout autre statut. Elle ne contient jamais de texte de modèle, de message de moteur ni de nom d'interne.

Les 12 codes

Le status dit l'issue, le code dit le cas précis. Branchez sur code : deux codes très différents partagent parfois un statut. Quatre codes seulement sont des refus — les autres sont des constats, et les traiter comme des erreurs surestimerait la sévérité du système.

4 · Les 8 tools

answer_question

Réponse documentaire sourcée

Visible par : dev support commercial admin

Arguments

ArgumentTypePrésenceContrainte
questionstringrequis—
collectionsarrayoptionneltableau de string

Réponse

Statuts possibles
error · hors_corpus · ok · refused
Clés de charge utile
answer · sources absentes sur un refus ou une non-réponse

Description servie — elle diffère selon le profil

Servie à : dev

Objet
répondre à une question sur la documentation interne Sorabel, en citant les documents utilisés.
Entrée
`question`, en langage naturel. `collections` restreint aux types de documents voulus, et peut être omis.
Sortie
une réponse rédigée et la liste de ses sources (référence, titre) ; ou une non-réponse quand le corpus ne porte pas de quoi répondre.
Utiliser quand
la question porte sur une procédure, une consigne interne, une notice, ou une caractéristique de produit.
Ne pas utiliser quand
la question attend un chiffre ou un état tenu par la base — la documentation décrit, elle ne compte pas. Pour les extraits bruts sans rédaction, utiliser search_docs.

Servie à : support, commercial, admin — seules les rubriques ci-dessous changent

Ne pas utiliser quand
la question attend un chiffre ou un état tenu par la base — la documentation décrit, elle ne compte pas. Pour les extraits bruts sans rédaction, utiliser search_docs. Pour l'état d'un produit et non sa description — stock, chiffres, commandes —, utiliser ask_database. Un seul cas demande DEUX appels, et c'est le seul : une référence donnée SEULE, sans question — « REF-5313 ». Appeler alors AUSSI check_stock, et rendre la fiche ET le stock. Hors de ce cas, un seul tool suffit.

Statuts possibles

Description servie

Objet
rendre les extraits documentaires les plus pertinents pour une recherche, sans rédiger de réponse.
Entrée
`query`, mots-clés ou question. `collections` restreint aux types de documents voulus, et peut être omis.
Sortie
les extraits classés par pertinence, avec leurs métadonnées — identifiant d'édition, titre, type, thème.
Utiliser quand
il faut lire le texte source lui-même, comparer plusieurs passages, ou obtenir l'identifiant d'une édition.
Ne pas utiliser quand
une réponse formulée est attendue, plutôt que des extraits. Pour une réponse rédigée et sourcée, utiliser answer_question. Pour le texte intégral d'une édition identifiée, utiliser get_document.

get_document

Texte intégral d'un document

Visible par : dev support commercial admin

Arguments

ArgumentTypePrésenceContrainte

Réponse

Statuts possibles
error · hors_corpus · ok · refused
Clés de charge utile
text · metadata absentes sur un refus ou une non-réponse

Description servie

Objet
rendre le texte intégral d'une édition documentaire déjà identifiée.
Entrée
`doc_id`, un identifiant d'édition de la forme `notices/notice-REF-1589-v1.0`. `version` peut être omis.
Sortie
le texte complet et les métadonnées de l'édition ; ou une non-réponse quand aucune édition ne porte cet identifiant.
Utiliser quand
l'identifiant d'édition est déjà connu, parce qu'un autre tool documentaire vient de le rendre.
Ne pas utiliser quand
l'entrée est une question en langage naturel, ou une référence produit de la forme REF-NNNN — une référence produit n'est pas un identifiant d'édition, et ce tool ne la trouvera pas. L'identifiant attendu est celui que rend search_docs. list_sources en donne l'inventaire. Pour une question, ou pour une référence produit REF-NNNN, utiliser answer_question.

Objet
traduire une question chiffrée en une lecture SQL de la base commerciale, et l'exécuter.

`question`, en langage naturel.
